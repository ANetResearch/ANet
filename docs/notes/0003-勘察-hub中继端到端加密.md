# 03 · hub 中继内容的端到端加密:现状与信封设计

- 调研日期:2026-09-26
- 范围:ANetCore(`59086ea`, v0.14.0)、ANet(`840b8ea`)、ANetHub(`8a64f49`),路径均相对 `/data/projs/anet-oss/`
- 方法:只读代码与文档,未修改任何仓库文件,未运行测试或复现攻击。
- 标注约定:未加标注的陈述均由阅读代码核实,并给出 `文件:行`;标 **[推断]** 的是推理或设计建议,未经运行验证。

## 0. 结论摘要

1. `ANetCore/identity/encrypt.go` 已有匿名 sealed box(`SealTo`/`Open`),但在 ANet、ANetHub、ANetLink 的非测试代码中**没有任何调用点**。当前所有中继载荷都是明文 CoreDet-CBOR,hub 与链路上的任何观察者都能读取任务目标、对话正文、交付物、附件字节和支付授权。
2. hub 侧有三处代码**实际解码或终结**了中继内容,与"hub 只做传输"的决定直接冲突:管理面 harvester 把中继载荷解码成数据集(`ANetHub/internal/admin/harvest.go:151-196`);访客模式由 hub 充当会话一方,构造并解码载荷(`ANetHub/internal/aghub/guest.go:547-614`);评价上传要求并公开展示请求 TaskDoc 与交付物全文(`ANetHub/internal/aghub/server.go:630-633, 725-731`)。
3. 当前中继的发送方认证不完整:`/relay/send` 不做认证(`server.go:243-245, 1081-1083`),`ChatMsg` 不签名(`ANetCore/delegation/delegation.go:129-132`),接收方把 hub 转交的 `from_aid` 当作发送者(`ANet/internal/daemon/relay.go:424`),`ingestMessage` 不检查发送者是否为该交互的对端(`ANet/internal/daemon/delegation.go:636-686`)。`DelegateReq` 的签名只覆盖 TaskDoc,不覆盖 InteractionID、附件和支付(`delegation.go:37-55`),TaskDoc 本身没有时间戳、随机数或收件人(`ANet/internal/daemon/daemon.go:281-291`)。由此可推出一条"改换 interaction id 重放已签名委派、使 provider 重复执行(含已付费能力)"的路径 **[推断,未复现]**,详见 §2.3。
4. hub 为路由真正需要的字段只有 `to_aid`、载荷大小和入队时间。`from_aid`、`kind`、`interaction_id` 目前只用于统计(`completed_task`)、harvester 和接收端分派,都可以移入密文。
5. 推荐信封:外层只暴露 `{v, to, suite, kid, enc, ct}`;加密用 RFC 9180 HPKE Base 模式(Go 1.26 标准库 `crypto/hpke`,三个仓库 `go.mod` 均为 `go 1.26.6`,无需新依赖);发送方认证用信封内的 Ed25519 签名,签名覆盖收件人、类型、交互 id、消息 id、时间戳、过期时间、正文和 HPKE `enc`;收件人加密公钥不再从身份签名密钥推导,而是作为独立轮换的 X25519 密钥发布在已签名的 AgentCard 扩展里,以获得有界前向保密;交互内后续消息改用交互级临时密钥;大附件用 STREAM 分块 AEAD 单独传输,信封内只放清单与内容密钥。详见 §5。

## 1. 现有加密原语:`ANetCore/identity/encrypt.go`

### 1.1 行为

| 项 | 事实 | 位置 |
|---|---|---|
| 密钥来源 | X25519 私钥 = `SHA-512(ed25519 seed)[:32]` 经 clamp,即 Ed25519 签名标量;X25519 公钥 = Ed25519 公钥点的 Montgomery-u 坐标 | `encrypt.go:3-8, 33-58` |
| 构造 | libsodium `crypto_box_seal`:每条消息新生成临时 X25519 密钥,nonce = `blake2b-24(eph_pub ‖ recipient_pub)`,线上格式 `eph_pub(32) ‖ box` | `encrypt.go:10-12, 60-88` |
| 发送方认证 | 无。注释写明"pair with a signature if you need it" | `encrypt.go:12` |
| 解密密钥 | `Open` 只用 `c.cur`(当前签名密钥) | `encrypt.go:90-108` |
| 轮换后行为 | 封给轮换前密钥的密文在轮换后无法打开,测试把这一点固定下来 | `encrypt_test.go:70-90` |
| 密钥复用说明 | 作者注明 sign 与 DH 共用一把密钥"couples the two algorithms",专用加密密钥是"possible future hardening" | `encrypt.go:14-17` |
| 上下文绑定 | 无 AAD/info 参数;密文不绑定收件人 AID、消息类型或交互 | `encrypt.go:73-88` |
| 小阶点 | `X25519PublicFromEd25519` 只做 `edwards25519.Point.SetBytes`,不拒绝小阶点;`nacl/box` 的 `Precompute` 直接调用 `curve25519.ScalarMult`,不检查全零共享密钥 | `encrypt.go:47-58`;`~/go/pkg/mod/golang.org/x/crypto@v0.55.0/nacl/box/box.go:81-84` |
| 调用点 | 非测试代码中无调用。唯一提及是 `identity.go:97-98` 注释建议可用于静态加密控制器导出 | `grep` 结果;`ANetCore/identity/identity.go:94-98` |

### 1.2 与身份层的耦合

- `Controller` 只保存当前与下一把私钥(`identity.go:177-182`),导出格式也只含这两把种子(`identity.go:99-103`)。退役的私钥不保留,因此以身份密钥为加密密钥时,轮换即丢失对在途密文的解密能力。
- `CurrentPrivateKey` 注释允许把同一把密钥作为 libp2p 主机密钥(`identity.go:228-233`)。若再用于 DH,同一标量将同时服务于 Ed25519 签名、X25519 DH 和传输层握手。
- ANet 中没有 `Rotate(` 调用点(对 `ANet/` 全量 grep 无结果),即 daemon 目前从不轮换身份密钥,上述轮换问题在生产中处于潜伏状态。

### 1.3 评估

- 作为"单条消息、收件人静态密钥、不需要发送方认证"的原语,实现与 libsodium 一致,测试覆盖了往返、错收件人、篡改和轮换后失效(`encrypt_test.go:20-106`)以及公私钥推导等价性(`encrypt_internal_test.go:12-31`)。
- 作为中继 E2E 的基础不够:没有上下文绑定,没有发送方认证,没有前向保密,解密密钥随身份轮换立即失效,且与签名密钥共用。§5 的方案不复用它 **[推断]**。

## 2. 经 hub 中继的全部载荷

### 2.1 通道

- 所有中继发送都经过 `relaySend`,它按顺序尝试已注册的传输(p2p 在前,hub 兜底)(`ANet/internal/daemon/transport.go:74-131`)。
- hub 传输把 `{to_aid, from_aid, kind, interaction_id, payload(base64)}` POST 到 `/relay/send`(`transport.go:31-47`)。
- 接收:后台循环每秒 `POST /relay/poll`(KEL 签名挑战)(`relay.go:32-35, 265-280`),逐条 `dispatch`,再 `ack`(`relay.go:373-397, 410-428`)。p2p 入站走 `inbound.Receive`,进入同一个 `dispatch`(`transport.go:167-191`)。
- p2p 帧同样携带明文 `From/To/Kind/IX/Payload`(`ANet/module/p2p/transport.go:30-57, 237-251`)。参考 peer 进程 `anetpeer` 支持 `tcp://host:port`,TCP 链路无加密、无认证(`ANet/tools/anetpeer/main.go:11-19, 332-348`)。
- 生产测试拓扑中 fmax hub 以明文 HTTP 按 IP 访问(`ANet/scripts/prodtest.sh:12-13, 100-101`)。因此当前中继内容在公网上以明文传输,读取者不限于 hub 运营方。

### 2.3 接收侧认证缺口(当前代码)

以下各项按 CLAUDE.md 要求给出位置、行为、影响、发现方式。发现方式均为本次代码阅读。

- **D1 聊天消息无发送方认证。**
  位置:`ANetCore/delegation/delegation.go:129-132`;`ANet/internal/daemon/relay.go:424`;`ANet/internal/daemon/delegation.go:636-686`;`ANetHub/internal/aghub/server.go:243-245, 874-931`。
  行为:`ChatMsg` 不签名;接收方把 relay 元数据中的 `from_aid` 作为发送者;`/relay/send` 不认证,`from_aid` 由调用方任意填写;`ingestMessage` 只检查交互存在(`delegation.go:642-644`),不检查 `fromAID == ix.PeerAID`。
  影响:知道 interaction id 的任何人(hub、链路观察者、联邦中转 hub)可向交互注入正文或 `end_request`/`end_accept`。provider 构建记录时,凡 `SenderAID != provider` 一律标为 `requester`(`delegation.go:362-365`),注入内容会进入 provider 签名的对话记录;伪造的 `end_accept` 可触发 `maybeFinalize` 出具回执(`delegation.go:670-681, 375-436`)。

- **D2 委派签名不绑定 interaction id、收件人、时间。**
  位置:`ANet/internal/daemon/daemon.go:281-291`(TaskDoc 只含 Intent);`ANet/internal/daemon/capability.go:155-160`;`ANetCore/tsir/taskdoc.go:95-105`;`ANetCore/delegation/delegation.go:37-55, 197-217`。
  行为:TaskDoc 原像不含时间戳、随机数、收件人或 interaction id;`VerifyDelegateReq` 只检查 InteractionID 非空并以 `msgTime=now` 验签。
  影响:(a) 已捕获的 `DelegateReq` 可改写 InteractionID 后重新投递,provider 的去重以 interaction id 为键(`delegation.go:528-539`),会当作新任务处理;(b) 收到委派的 provider 可把同一份已签名 TaskDoc 转投第三方,第三方看到的是原请求方的有效签名;(c) 附件与支付可被替换或删除而签名仍然有效。

- **D3 付费委派的重放结算被当作新付款 [推断,未复现]。**
  位置:`ANetHub/internal/aghub/facilitator.go:173-195`;`ANet/module/x402/x402.go:236-260`;`ANet/internal/daemon/capability.go:339-372`。
  行为:facilitator 对已结算的授权返回 `Success:true` 并附 `Extensions["anet.replayed"]=true`;全仓 grep 显示该标记无消费方;provider 侧 `Settle` 不比对授权中的 `InteractionID` 与当前委派的 interaction id(ANet 中 `InteractionID` 仅在 `pay.go:164` 授权签发时出现)。
  影响:与 D2(a) 组合,改换 interaction id 的重放会通过结算并再次执行已付费能力,不产生新扣款。对有物理副作用的能力(shell、设备)即重复执行。此链路由逐段阅读推出,未运行复现。

- **D4 失败结果不验证。**
  位置:`ANet/internal/daemon/delegation.go:695-701`。
  行为:`Status == failed` 时直接 `SetFailed`,不检查回执或发送者。
  影响:知道 interaction id 的任何人可把请求方的外发交互标记为失败。

- **D5 KEL 缓存与 hub 注册均允许回退。**
  位置:`ANet/internal/daemon/peerkel.go:47-65`;`ANet/internal/daemon/paylink.go:86-88`;`ANetHub/internal/aghub/aghub.go:466-470`;`server.go:486-501`。
  行为:`peerKELs.remember` 不验证、总是覆盖(注释称"a later KEL is a longer key history",但未检查长度或前缀);`paylink.go:86-88` 注释称 "remember verifies before storing",与实现不符。hub 重新注册时以提交的 KEL 验证挑战,`PutAgent` 无条件覆盖存储的 KEL,不检查新 KEL 是否为旧 KEL 的延伸。
  影响:目前主要影响验签;引入加密后,持有已退役密钥的一方可用截断的 KEL 重新注册,使 hub 对外发布的"当前密钥"回退到已泄露的旧密钥,发送方据此加密即被读取 **[推断]**。

这些缺口不属于加密本身,但信封设计必须同时关闭它们:仅加密而不在信封内认证发送方,hub 仍可伪造聊天与失败结果。

3. 访客模式(`guest.go`):hub 是会话端点,违反"hub 只做传输"。两个方向 **[推断]**:移出 hub,改由一个官方公开 agent 进程承担(与决定 3 的"官方公开 agent"一致);或在浏览器内用 WebCrypto 生成临时身份并直接做 E2E,hub 只中继密文。
4. 评价展示 goal/deliverable(`server.go:630-633, 661-667, 725-731`;`aghub.go:85-102`):改为只收 receipt 与 review(CID 锚点),不收内容全文。
5. 联邦信封中的 `from_aid/kind/interaction_id`(`federation.go:107-124, 133-135`):删除,只保留 `dest_aid` 与密文。
6. p2p 帧中的 `From/Kind/IX`(`p2p/transport.go:44-52`)与 `module.Transport.Send` 的 `kind, interactionID` 参数(`ANet/module/transport.go:33`):改为只传 `toAID` 与信封字节。

## 4. 密码学设计评估

### 4.1 发送方封给哪把密钥;收件人轮换后怎样

现状:没有加密调用点,也就没有"封给哪把密钥"的逻辑。若直接采用 `SealTo`,只能封给 KEL 头部的当前签名密钥,轮换后收件人信箱里尚未取走的消息全部无法解密(`encrypt.go:90-98`,`encrypt_test.go:70-90`),而信箱中未投递消息最长保留 14 天(`hub-db-roll.sh:5, 21`)。

评估与建议 **[推断]**:

1. **加密密钥与身份密钥分离。** 每个 daemon 维护独立的 X25519 加密密钥(下称 enc key),由身份密钥签名发布。好处:(a) 消除 sign/DH 共钥(`encrypt.go:14-17`);(b) enc key 可按自己的周期轮换,不依赖 KEL 轮换(ANet 目前没有 KEL 轮换调用点);(c) 退役 enc key 可以在保留期后删除,获得有界前向保密(§4.2)。
2. **发布位置:已签名 AgentCard 的扩展字段。** `adp.AgentCard` 有 `Extensions map[string]any` 并且在签名原像内(`ANetCore/adp/adp.go:151-191`);hub 接收卡片时按 KEL 验签并执行 seq 高水位规则(`ANetHub/internal/aghub/card.go:43-72`);hub 通过 `GET /agents/{aid}/card` 对外提供(`server.go:198`)。hub 无法伪造卡片;它能做的是提供旧卡片。
3. **发送方选择规则。** 取已验证卡片中未过期、首选套件的最新 enc key;在交互内部优先使用对端在本交互中给出的临时回复密钥(§4.2)。发送方本地缓存每个 AID 的卡片 seq 高水位与 KEL,只接受延伸(前缀一致且更长)的 KEL,拒绝分叉与回退。这需要修正 D5。
4. **KEL 轮换后的规则。** 卡片签名在某个 `key_state_seq` 下做出。发送方只接受"签名 seq 等于已知 KEL 头部 seq"的卡片中的 enc key:KEL 轮换通常意味着旧签名密钥可能泄露,旧密钥签发的 enc key 列表不应继续被信任,轮换后必须由新密钥重新签发卡片。
5. **收件人保留退役 enc 私钥。** 保留至 `not_after + 最长信箱留存期(当前 14 天)`,然后删除。收件人按外层 `kid` 选私钥;`kid` 未知时 ack 并丢弃,记录 "sealed to unknown key"。发送方在超时后刷新卡片重发。
6. **hub 提供旧卡片或截断 KEL 时。** 若旧 enc key 尚未过期,收件人仍持有其私钥,通信正常且机密;若已过期,发送方拒绝使用,投递以明确错误失败,而不是降级为明文。hub 侧应同时拒绝非延伸 KEL 的重新注册(修正 `aghub.go:466-470`)。

### 4.2 前向保密

现状:sealed box 的临时密钥只提供"发送方事后无法解密";收件人静态私钥一旦泄露,所有曾封给它的历史密文都可解密。hub 保存密文 7-14 天并有周备份(`hub-db-roll.sh:4-9, 43-54`),daemon 私钥以种子形式存在磁盘(`identity.go:90-109`)。"先存后解"对这一部署是现实场景:取得 hub 数据库或备份的一方,只要日后取得某个 daemon 的密钥文件,即可解密该 daemon 的历史收件。

| 方案 | 前向保密粒度 | 异步/离线收件 | 与至少一次投递、多传输的兼容性 | 复杂度 |
|---|---|---|---|---|
| A 收件人静态身份密钥(当前 `SealTo`) | 无 | 支持 | 兼容 | 低 |
| B 定期轮换的已签名 enc 预密钥(如 7 天) | 以轮换周期加保留期为界(约 3 周) | 支持 | 兼容 | 低 |
| C B + 交互级临时密钥(委派携带请求方临时公钥,provider 首条回复携带己方临时公钥,交互终结后双方删除) | 首条消息同 B;其后按交互 | 支持 | 兼容;删除时机须晚于信箱留存期 | 中 |
| D Double Ratchet / MLS | 按消息,并有被入侵后恢复 | 需要状态同步 | 至少一次重投递和 hub/p2p 双路径会造成乱序与重复,需要额外处理 | 高 |

建议 **[推断]**:采用 C。理由:任务型交互消息数少、持续时间有限,交互级密钥已把暴露窗口缩到单个交互;D 的状态机与"消息可能经 hub 与 p2p 两条路重复到达"的现有投递语义(`transport.go:97-131`,`delegation.go:162-178`)不匹配,收益主要在长期对话,不在本场景。同时建议 hub 在 ack 时删除载荷行,而不是保留 7 天,以缩短密文留存。

后量子:Go 1.26 `crypto/hpke` 提供 `MLKEM768X25519`(X-Wing,draft-ietf-hpke-pq)(`~/go/pkg/mod/golang.org/toolchain@v0.0.1-go1.26.6.linux-amd64/src/crypto/hpke/pq.go:20-43`;`kem.go:54-61`)。"先存后解"正是后量子攻击的威胁模型。建议在信封中保留 `suite` 字段,首版 MTI 为 X25519 套件,混合套件作为可选并在跨语言实现可用后考虑设为默认 **[推断]**。代价:ML-KEM-768 封装公钥 1184 字节、密文 1088 字节(常量名见 `pq.go:28-29`),对卡片与每条消息都是可接受的开销。

### 4.3 重放

现状见 §2.3 D1-D3:没有消息级新鲜度和收件人绑定;委派去重只以 interaction id 为键;聊天去重依赖不受认证的 `MsgID`(`delegation.go:162-178, 646-659`)。邮箱鉴权挑战有 5 分钟时间窗(`ANetCore/relayauth/relayauth.go` 中 `MaxSkewMillis = 5*60*1000`;hub 校验 `server.go:1028-1045`),但只保护 poll/ack,不涉及载荷。

建议 **[推断]**:

1. 内层签名覆盖 `to`、`ix`、`mid`(16 字节随机消息 id)、`ts`、`exp`。
2. 接收方维护 `(from, mid)` 重放表,条目保留到 `exp`。重复的 `(from, mid)` 按"已处理"ack,不再执行。这同时覆盖现有至少一次投递的去重需求,可替代 `ChatMsg.MsgID` 的角色。
3. `exp - ts` 上限取 15 天(覆盖 14 天信箱留存);`ts` 超前本地时钟超过 5 分钟即拒绝(沿用 relayauth 的容差)。
4. 业务层绑定:`DelegateReq.InteractionID` 必须等于内层 `ix`;x402 授权的 `InteractionID` 必须等于内层 `ix`;`anet.replayed=true` 的结算只能对应本节点已记录的同一 interaction,否则拒绝执行。
5. 同一逻辑消息在 hub 与 p2p 上重试时复用同一份信封字节,保证 `mid` 与 `enc` 不变。

### 4.4 信封内的发送方认证

HPKE Base 模式与 sealed box 一样是匿名的。可选做法:

| 做法 | 评价 |
|---|---|
| HPKE Auth 模式(发送方静态 DH 密钥参与) | Go 标准库只实现 Base 模式(`hpke.go:47-54` 固定 `mode 0` 与空 PSK);Auth 模式存在密钥泄露冒充(KCI)问题;认证强度依赖发送方 DH 密钥的发布与轮换,又引入一套密钥 |
| 先加密后签名(外层签名) | 外层签名暴露发送方身份给 hub;攻击者可剥离签名换上自己的签名冒领 |
| 先签名后加密,签名不含收件人 | 收件人可把已签名内容重新加密转给第三方,冒充"发送方发给你的"(Davis 2001 "Defective Sign & Encrypt" 描述的问题) |
| **先签名后加密,签名覆盖收件人与 HPKE `enc`** | 推荐。hub 看不到发送方;签名绑定收件人,阻止转投;绑定 `enc` 使签名只对这一个密文有效 |

HPKE 的 `NewSender` 先返回 `enc`,再调用 `Seal`(`hpke.go:126-178`),因此"签名覆盖 `enc`"可实现。

不可否认性:Ed25519 内层签名意味着收件人可以向第三方证明发送方说过什么。这与 anet 的证据模型一致(回执、评价、支付授权均为可出示的签名对象),视为设计属性而非缺陷 **[推断]**。

发送方身份解析:内层携带发送方 AID 与 `key_state_seq`,首次接触或轮换后附带 KEL(与现在 `DelegateReq.KEL`、`ResultResp.KEL` 的做法一致,`delegation.go:40, 101`)。验签复用 `identity.VerifyObject(kel, from, seq, ts, preimage, sig)`,其时间感知撤销门会拒绝轮换后仍用旧密钥签的新消息(`identity.go:493-544`,`rotationgate_test.go:13-44`)。

### 4.5 hub 必须看到的元数据及其泄露

hub 必须看到:`to_aid`(信箱路由)、密文长度(上限与 poll 预算)、入队与取件时间、发送与取件的来源 IP、poll 请求中的签名 AID。可选看到:`kid`(收件人密钥纪元)、`suite`。

`kind` 不需要。保留它会暴露交互生命周期(委派 → 若干消息 → 结果)和完成数;保留 `interaction_id` 会把消息串成会话;保留 `from_aid` 会直接给出社交图。三者均建议移入密文。

E2E 后仍存在的泄露(如实记录):

1. **收件方与流量模式。** `to_aid`、时间、次数必然可见。
2. **发送方可由 IP 关联。** `/relay/send` 即使不带 `from_aid`,发送方 daemon 同时用同一 IP 签名 poll 自己的信箱,hub 运营方主动关联 IP 与时间即可推出大部分发送方。删去 `from_aid` 的收益是:hub 数据库、备份、联邦中转方和管理面不再**存储**社交图;对主动关联的运营方不构成隐藏。更强的隐藏需要匿名网络,不在本范围 **[推断]**。
3. **长度。** 附件最大 64 MiB(`ANet/internal/daemon/attachments.go:23-26`),长度可区分文本、图片、压缩包。建议对内层明文做 Padmé 填充(PURB 论文提出,开销上限约 12%) **[推断]**,附件密文按块取整。
4. **x402 结算。** hub 作为 facilitator 看到 payer、payee、金额和授权中的 interaction_id(`facilitator.go:176-180`)。E2E 后 hub 无法再把它与中继消息按 interaction_id 直接对应,但可按时间关联。可选:授权中改放 `H(interaction_id)` **[推断]**。
5. **公开面。** 注册名、能力、profile、卡片、评价关系是公开设计,不在 E2E 范围。

反滥用:`/relay/send` 不认证是现有设计(`server.go:1081-1083`)。E2E 后 hub 无法按发送方限流,只能按 IP 和收件方信箱配额限流;在"默认不接受任何委派"的决定下,垃圾消息会在收件方解密后被丢弃,但仍消耗 hub 存储和收件方带宽。第二阶段可引入信箱访问令牌:收件人在 hub 登记若干令牌的哈希,发送方在外层出示令牌,hub 只校验令牌不识别发送方;公开 agent 设为 open 模式 **[推断]**。

### 4.6 大附件

现状:附件字节内联在载荷中,单个上限 64 MiB(`attachments.go:26`);hub 请求体上限 1 GiB(`server.go:127`);单次 poll 预算 48 MiB(`aghub.go:979`);daemon 响应上限 256 MiB(`hub_client.go:27-31`);长传输被中断会导致消息无法 ack 而反复重投(`relay.go:37-42`)。附件 CID 是明文字节的 `SumRaw`(`delegation.go:59-66`),目前对 hub 可见,hub 可据此确认某个已知文件是否被传输。

对单次 AEAD 的评估:把 64 MiB 附件整体放进一次 HPKE `Seal` 在密码学上没有问题,但两侧都必须整体缓冲,出错只能整体重传,且继续挤占信箱的 poll 预算。

建议 **[推断]**:

1. 每个附件生成随机 32 字节内容密钥,用 STREAM 分块 AEAD 加密(ChaCha20-Poly1305,64 KiB 块,nonce = 计数器 ‖ 末块标志;可直接采用 age v1 payload 规格,Go/Rust/JS 均有独立实现)。
2. 密文作为 blob 单独上传(hub blob 存储、p2p 或将来的 CAS),以密文 CID 寻址;hub 只看到密文 CID 与长度。
3. 内层信封只携带清单:`{name, mime, size, plaintext_cid, key, blob_cid, blob_size, chunk}`。收件方下载后流式解密并校验 `plaintext_cid`,现有 `verifyAttachment` 的语义保留(`attachments.go:108-127`)。
4. 不采用收敛加密(密钥由内容派生),因为它向 hub 暴露"两份附件是否相同"。
5. 小附件(如 ≤ 256 KiB)可继续内联在内层以减少往返。
6. blob 路径建立后,`/relay/send` 的请求体上限可从 1 GiB 大幅下调,信箱只承载小消息。
7. 同一附件发给多个收件人时可只加密一次,为每个收件人分别封装内容密钥,适用于后续的组织/黑板场景。

### 4.7 其他

- 静态存储:enc 私钥应与身份导出分开存放(身份导出格式固定两把种子,`identity.go:99-103`),以便到期删除。前向保密依赖实际删除 **[推断]**。
- 小阶点:Go `crypto/ecdh` 的 X25519 在共享密钥为全零时返回错误(`~/go/pkg/mod/golang.org/toolchain@v0.0.1-go1.26.6.linux-amd64/src/crypto/ecdh/x25519.go:86`),HPKE DHKEM 经由该路径;现有 `nacl/box` 路径不检查(见 §1.1)。
- 传输层 TLS 仍然需要,用于保护 poll 鉴权挑战与元数据,但不再承担内容机密性。

## 5. 推荐信封格式(ANet 封装信封 v1) **[推断]**

### 5.1 结构

编码沿用仓库约定的 CoreDet-CBOR 整数键映射。

外层 `SealedEnvelope`(hub 可见):

```
SealedEnvelope = {
  1: v      uint        ; = 1
  2: to     tstr        ; 收件人 AID,路由用
  3: suite  uint        ; 1 = HPKE(DHKEM-X25519-HKDF-SHA256 0x0020, HKDF-SHA256 0x0001, ChaCha20-Poly1305 0x0003)
                        ; 2 = HPKE(MLKEM768-X25519 0x647a, HKDF-SHA256, ChaCha20-Poly1305),可选
  4: kid    bstr .size 16 ; 收件人 enc 公钥 id = SHA-256("anet-enc-kid/v1" ‖ suite ‖ pub)[:16]
  5: enc    bstr        ; HPKE 封装密钥(套件 1 为 32 字节)
  6: ct     bstr        ; HPKE 密文(明文为 SealedInner)
  ? 7: access bstr      ; 第二阶段:信箱访问令牌
}
HPKE info = CoreDet-CBOR({1: "anet-relay/v1", 2: to, 3: suite, 4: kid})
HPKE aad  = 空
```

`info` 把收件人与密钥 id 绑定进密钥调度:hub 改写 `to` 或 `kid` 会导致解密失败。

内层 `SealedInner`(密文内):

```
SealedInner = {
  1:  from  tstr        ; 发送方 AID
  2:  seq   uint        ; 发送方签名所用 key_state_seq
  3:  to    tstr        ; 必须等于外层 to
  4:  type  tstr        ; "anet.delegate/1" | "anet.result/1" | "anet.message/1" | "a2a.<op>/1" ...
  5:  ix    tstr        ; interaction id(无交互的消息为空串)
  6:  mid   bstr .size 16 ; 随机消息 id
  7:  ts    uint        ; unix ms,发送方时钟
  8:  exp   uint        ; unix ms,过期后拒收;exp - ts ≤ 15 天
  9:  body  bstr        ; 类型化正文:现有 DelegateReq/ResultResp/ChatMsg 的 CBOR,或 A2A 消息 JSON
  ? 10: kel bstr        ; 发送方 KEL(首次接触或轮换后)
  ? 11: rk  bstr        ; 发送方为本交互生成的临时回复公钥
  ? 12: atts [* AttachmentRef] ; 大附件清单(§4.6)
  20: sig   bstr .size 64 ; Ed25519
  21: pad   bstr        ; 全零填充,不在签名内
}
SigPreimage = CoreDet-CBOR({0: "anet-relay-sig/v1", 1..12 同上, 30: outer.enc, 31: outer.kid, 32: outer.suite})
```

### 5.2 enc key 发布

AgentCard `Extensions["anet.enc/v1"] = [{kid, suite, pub, not_before, not_after}]`,随卡片由身份密钥签名(`adp.go:167-168, 181`)。建议 7 天轮换、相邻两把有效期重叠;私钥保留到 `not_after + 15 天` 后删除。该字段也可以作为 A2A AgentCard 的扩展参数暴露,便于其他 A2A 实现采用 **[推断]**。

### 5.3 发送流程

1. 解析收件人:交互内若对端给过 `rk`,封给 `rk`;否则取已验证卡片中的 enc key(卡片验签、seq ≥ 本地高水位、卡片签名 seq 等于已知 KEL 头部 seq、enc key 未过期)。
2. 组装 inner,签名,按 Padmé 填充,HPKE 加密。
3. 将同一份信封字节交给 `relaySend` 的传输列表;重试复用同一份字节。

封装应位于 `relaySend` 之前的单一位置(`transport.go:104`),使 hub、p2p 及以后的传输共享同一封装;`module.Transport.Send` 改为 `Send(ctx, toAID string, envelope []byte)`(现签名见 `ANet/module/transport.go:33`)。

### 5.4 接收流程(按顺序,任一步失败即 ack 并丢弃,记录原因)

1. `v` 已知;外层 `to` 等于本节点 AID。
2. 以 `kid` 在密钥环中查私钥(有效期内的 enc key、保留期内的退役 enc key、未过期的交互临时密钥)。
3. HPKE Open(`info` 如 5.1)。
4. 解码 inner;inner.`to` 等于外层 `to`。
5. `now ≤ exp`;`ts ≤ now + 5 min`;`exp - ts ≤ 15 天`。
6. 解析发送方 KEL:inner 携带时须 `Replay` 通过、推导出 `from`、且是本地缓存的延伸;否则用缓存;否则从 hub 取并做同样检查。
7. `identity.VerifyObject(kel, from, seq, ts, SigPreimage, sig)`。
8. 重放表:`(from, mid)` 已存在则 ack 且不处理。
9. 授权:`anet.delegate/1` 按收件人的发送方策略(默认拒绝,公开 agent 例外);`message`/`result` 要求交互存在且 `from == ix.PeerAID`。
10. 正文校验:`DelegateReq.InteractionID == ix`;`VerifyDelegateReq`/`VerifyResult` 照旧;失败结果同样须经过第 7、9 步;x402 授权的 `InteractionID == ix`,`anet.replayed` 仅在同一 interaction 已记录时接受。
11. 分派(替代现有 `dispatch` 的 `m.Kind` 分支,`relay.go:418-427`)。

未封装的载荷默认拒绝(配置项 `require_sealed` 默认开),不做明文回退。

### 5.5 hub 侧对应改动

- `/relay/send` v2 只接收 `{to_aid, envelope}`,不存储 `from_aid/kind/interaction_id`;C2 线协版本号递增(`hubapi.go:80-83`,`server.go:150-176`),契约测试同步(`ANet/internal/hubapi/hubapi_test.go:118-130` 目前固定三种 kind)。
- ack 即删载荷行;调整 `hub-db-roll.sh`。
- 删除 harvester 的 `hub-relay` 数据源;评价改为只收 CID;访客模式迁出或改为浏览器端 E2E;`completed_task` 删除或替换;联邦信封删元数据字段;重新注册必须延伸已存 KEL。
- 新增 blob 上传/下载端点(不透明密文,有 TTL 与配额)。

### 5.6 选择理由与被否决的备选

| 选择 | 理由 | 被否决的备选及原因 |
|---|---|---|
| HPKE(RFC 9180)Base 模式 | IETF 标准,有官方测试向量;Go 1.26 标准库自带(`hpke.go:126-237`),三个仓库均为 go 1.26.6,无新依赖;支持 `info` 上下文绑定与套件演进(含后量子混合);MLS(RFC 9420)、OHTTP(RFC 9458)均建立在其上,面向 A2A 社区贡献时更易被接受 **[推断]** | 继续用 nacl sealed box:无上下文绑定、算法固定、与身份密钥耦合。JWE(ECDH-ES+X25519):与 A2A 的 JWS 卡片签名同属 JOSE(`Refs/a2a/docs/specification.md:2014-2074`),但 JSON 编码、算法协商面大;可作为将来的 JSON 映射,不作为主格式 |
| 内层 Ed25519 签名 | 复用现有 KEL、`VerifyObject` 与撤销门;hub 看不到发送方;与证据模型的不可否认性一致 | HPKE Auth 模式(标准库未实现,KCI);外层签名(暴露发送方,可被剥离替换) |
| 独立轮换的 enc key,经签名 AgentCard 发布 | 消除共钥;有界前向保密;hub 无法伪造;卡片已有 seq 高水位 | 身份密钥推导(无前向保密,轮换即不可解密);KEL 中新增事件类型(改动身份层,且 KEL 轮换本身尚未在 ANet 中使用) |
| 交互级临时密钥 | 以低复杂度把暴露窗口缩到单个交互 | Double Ratchet/MLS:状态与至少一次、多路径投递不匹配 |
| STREAM 分块附件 + 独立 blob | 流式、可部分重传、信箱只承载小消息、hub 只见密文 CID | 整体内联单次 AEAD:占 poll 预算、整体缓冲;收敛加密:暴露相等性 |
| 外层只留 `to` | 满足路由,其他字段 hub 均无必要用途 | 保留 `kind`:暴露生命周期与完成数,仅服务统计 |

与 A2A 的关系 **[推断]**:A2A 规范要求生产部署使用 TLS(`Refs/a2a/docs/specification.md:1877-1883`),没有端到端加密,也没有面向无法做 HTTPS 服务端的 agent 的传输。上述信封可以作为 A2A 自定义协议绑定提交(自定义绑定在 AgentCard `supportedInterfaces` 中以 URI 声明,`Refs/a2a/docs/topics/custom-protocol-bindings.md:15-35`),内层 `type = "a2a.<op>/1"` 承载标准 A2A 消息;a2a-x402 的 `x402.payment.payload` 位于 `message.metadata`(`Refs/a2a-x402-spec-v0.2.md:43, 269-289`),随内层加密传输,商户 agent(provider daemon)仍向 facilitator(hub)结算(`a2a-x402-spec-v0.2.md:137, 352`),与现有结算路径一致。

## 6. 测试要求(对照 CLAUDE.md) **[推断]**

- 契约向量:以冻结身份(`ANetCore/identity/suite.go:10-60` 的做法)加 `DeriveKeyPair` 固定的临时密钥,产出外层、内层、签名原像的黄金字节,供其他语言实现对照;HPKE 套件本身对 RFC 9180 测试向量。
- 变异验证:对每个签名字段(`to`、`type`、`ix`、`mid`、`ts`、`exp`、`enc`、`kid`、`body`)逐一改动,确认拒收;重放 `(from, mid)`;过期;发送方不是交互对端;封给已删除密钥;hub 改写外层 `to`。
- fake 完整契约:`hubfake_test.go` 目前按 `kind` 取信箱载荷(`ANet/internal/daemon/hubfake_test.go:586-611`),E2E 后 fake hub 不得解析载荷,只按 `to_aid` 存取。
- 联调:`scripts/joint.sh` 增加"hub 数据库中的载荷不含明文标记串"的断言(对 `relay_message.payload` 搜索任务目标原文);`scripts/prodtest.sh` 在明文 HTTP 的 fmax hub 上跑一遍跨 hub 委派与付费调用;p2p 路径经 `anetpeer` TCP 同样验证。
- 可插拔编译:E2E 属于 C2 线协的一部分,应为内核无 tag 代码,不能被 `-tags` 去掉;若 blob 存储作为 hub 可选模块,须按符号数双向验证。
