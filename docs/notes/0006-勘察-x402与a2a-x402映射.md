## 1. 结论摘要

1. **对象层已是 x402 v2**。`ANetCore/payment` 实现的是 x402 v2 的 `PaymentRequired / PaymentPayload / SettlementResponse / VerifyResponse`(`ANetCore/payment/payment.go:7-9,48,68-124`),字段名 `amount`、`accepted`、`resource` 与 v2 一致 [外部]。a2a-x402 v0.2 规范的示例用的是 x402 v1(`"x402Version": 1`、`maxAmountRequired`,`Refs/a2a-x402-spec-v0.2.md:185,241,290`);coinbase/x402 仓库的 `transports-v2/a2a.md` 在**同一组 metadata 键**下改用 x402 v2 对象 [外部]。因此 anet 的对象层不需要回退到 v1,需要改的是**承载位置**和**状态机**。
2. **承载位置与状态机需要整体替换**。现状是"报价是一次已结束的交互(签名结果 + 收据),付款是第二次新委派"(`ANet/internal/daemon/paylink.go:185-223`);a2a-x402 要求**同一个 Task** 进入 `input-required`,付款以带 `taskId` 的 Message 提交,merchant 按 `taskId` 取回它当初开出的 requirements(`Refs/a2a-x402-spec-v0.2.md:140,159-161,267-269`)。
3. **anet-credit 保留为自定义 x402 scheme**。x402 v2 把 `scheme` 和 `network` 作为实现自定义的标识,并鼓励非区块链网络使用 CAIP-2 形式 [外部],anet 已据此命名 `anet-credit` / `hub:<aid>`(`payment.go:11-17,56,66`)。但 **`hub:<aid>` 实际不满足 CAIP-2**:reference 限长 32 字符 [外部],而 AID 是 59 字符的 CIDv1 字符串(见 §5 D4)。
4. **链上 scheme(exact/EVM USDC)现阶段不是必需**。按决策 2,外部 A2A 客户端经自己的本地 daemon 入网,因此网内买卖双方都有 anet 身份和 hub 账户,`anet-credit` 足以覆盖。链上 scheme 的必要场景是"非托管结算"和"anet agent 向网外 merchant 付款",可以作为可插拔 scheme 后置;现在应先把 scheme 接缝做出来 [推断/建议]。
5. **发现两处可导致少付或付错人的缺陷**(均为阅读代码所得,未运行):
   - relay 路径上,提供方结算前后都不比对授权条款与自己的报价(收款方、金额、交互绑定),`capability.go:350-372`(§5 D1)。
   - hub 网关检查的是未签名的 `pp.Accepted`,结算的是已签名的内层 `Authorization`,凭证金额取自价目而非结算额,`gateway.go:310-333,357-375` 与 `facilitator.go:520-565`(§5 D2)。
6. **hub 目前能读到任务内容**。relay 载荷是明文 CBOR(`transport.go:40-46`),hub 按原样落库(`ANetHub/internal/aghub/aghub.go:915-917`);其中包括 TaskDoc(目标、参数)、交付物,以及报价与付款对象。`ANetCore/identity/encrypt.go` 已有 `SealTo`/`Open`,但 ANet 与 ANetHub 的非测试代码中没有调用点(§5 D3)。在支付上,"hub 只见付款元数据"要靠端到端加密实现,x402 本身不提供这一点。
7. **x402 协议面有若干不合规之处**:facilitator 请求缺少 `paymentRequirements`;`/supported` 缺少 `extensions`、`signers`;错误原因大多是散文而非错误码,无法映射到 `x402.payment.error`(§5 D5、D6)。
8. **缺少付款上限**。MCP `task_delegate pay=true` 与 `delegate --pay` 会按对方报价全额付款,代码中没有上限,只有工具描述里的一句提醒(`mcpserv.go:71-74`,`paylink.go:232-253`)。这与"默认安全"不一致(§5 D7)。

### 2.5 现有的三条付款路径(`ANet/docs/PAYMENT-zh.md:57-122`)

1. 经中继的付费委派:`委派 → PAYMENT_REQUIRED(签名结果)→ 新交互 + DelegateReq.Payment → 提供方 /x402/settle → 干活 → 结果带 paid.receipt`。

3. 兑付:`Authorize(PayTo=hubAID) → POST /x402/redeem(hub)`(`pay.go:331-399`,`redemption.go:78-129`)。

## 3. 上游规范要点

### 3.1 a2a-x402 v0.2(本地 `Refs/a2a-x402-spec-v0.2.md`)

- 扩展 URI:`https://github.com/google-agentic-commerce/a2a-x402/blob/main/spec/v0.2`,"MUST use this URI"(`:11-13`)。
- 在 AgentCard 的 `capabilities.extensions` 中声明,建议 `required: true`(`:17-35`)。
- 两种流程:Standalone 把 requirements 放在 `task.status.message.metadata`,payload 放在 `message.metadata`;Embedded 放在 AP2 的 `CartMandate`/`PaymentMandate` 中(`:37-46`)。检测规则:有 `x402.payment.required` 键即为 Standalone(`:94-104`)。
- 角色:merchant 负责状态管理,按 `taskId` 取回当初开出的 requirements 并核对 payload(`:131-140`)。
- metadata 键(`:396-410`):`x402.payment.status`(每条 x402 相关消息必带)、`x402.payment.required`、`x402.payment.payload`、`x402.payment.receipts`(持久数组,记录完整历史,最终消息必带)、`x402.payment.error`。
- 状态值:`payment-required / payment-submitted / payment-rejected / payment-verified / payment-completed / payment-failed`(`:400-406`),状态迁移见 `:412-424`。
- Task 状态:要求付款时为 `input-required`(`:159-161`);成功后为 `completed`,也可以是 `working`(`:155,352`);失败时由实现决定,可以是 `failed`,也可以重新进入 `input-required`(`:432`)。
- 错误码(`:436-444`):`INSUFFICIENT_FUNDS / INVALID_SIGNATURE / EXPIRED_PAYMENT / DUPLICATE_NONCE / NETWORK_MISMATCH / INVALID_AMOUNT / SETTLEMENT_FAILED`。
- 激活方式:`X-A2A-Extensions` 头(`:426-428`)。
- 安全要求:必须验签、做输入校验、跟踪 nonce 防重放;传输"MUST use a secure transport layer like HTTPS/TLS"(`:474-480`)。
- 数据结构以 x402 核心规范为准(`:383-394`),示例全部为 x402 v1。

### 3.2 x402 v1 与 v2 的对象差异 [外部]

| 项 | v1 | v2 | anet 当前 |
|---|---|---|---|
| 402 体 | `{x402Version, error, accepts[]}` | `{x402Version, error?, resource{url,description,mimeType}, accepts[], extensions?}` | v2(`payment.go:69-75`) |
| 单个选项 | `scheme, network, maxAmountRequired, asset, payTo, resource(string), description, mimeType, outputSchema, maxTimeoutSeconds, extra` | `scheme, network, amount, asset, payTo, maxTimeoutSeconds, extra?` | v2(`payment.go:89-97`) |
| PaymentPayload | `{x402Version, scheme, network, payload}` | `{x402Version, resource?, accepted, payload, extensions?}` | v2,缺 `resource`(`payment.go:101-106`) |
| SettlementResponse | `success, errorReason?, transaction, network, payer` | 另加 `amount?`, `extensions?` | v2(`payment.go:116-124`) |
| `/verify` `/settle` 请求体 | `{x402Version, paymentPayload, paymentRequirements}` | 同左 | **缺 `paymentRequirements`**(`pay.go:214-216`,`facilitator.go:607-610,620-623`,`wire_federation.go:45-47`) |
| `/supported` | `{kinds[]}` | `{kinds[], extensions[], signers{}}` | 只有 `kinds`(`payment.go:127-129`) |
| network 名 | `base`, `base-sepolia` 等 | CAIP-2,如 `eip155:8453`;非区块链网络也建议用 CAIP-2(`ach:us`, `sepa:eu`) | `hub:<aid>`,不合规(D4) |
| HTTP 头 | `X-PAYMENT`, `X-PAYMENT-RESPONSE` | `PAYMENT-REQUIRED`, `PAYMENT-SIGNATURE`, `PAYMENT-RESPONSE` | v2(`payment.go:590-594`) |
| exact/EVM 载荷 | `{signature, authorization{from,to,value,validAfter,validBefore,nonce}}`(EIP-3009) | 同左,放在 `payload` 中 | 未实现 |

### 3.3 coinbase/x402 的 `transports-v2/a2a.md` [外部]

- 使用与 a2a-x402 v0.2 相同的 metadata 键和状态值,但对象为 `"x402Version": 2`(`accepted`、`amount`、`resource`)。
- 示例中的扩展 URI 为 `https://github.com/google-a2a/a2a-x402/v0.1`,与 v0.2 规范要求的 URI 不同;激活头仍是 `X-A2A-Extensions`。
- 错误表:`payment-rejected` 对应 Task `failed`;验证或结算失败对应 `failed` 加 `payment-failed`。
- [推断] 上游两份文档在 URI 和 x402Version 上不一致。anet 应在卡片中声明 v0.2 的规范 URI(v0.2 为 MUST),对象采用 v2,同时在读入时容忍 v1 的 `maxAmountRequired` / 顶层 `scheme,network`。

### 3.4 A2A v1.0 线协与 v0.2 扩展示例的差异

- a2a-x402 v0.2 的示例基于 A2A v0.3 线协(`"kind":"task"`、`"state":"input-required"`、`message/send`、`X-A2A-Extensions`)。
- A2A v1.0:枚举的 JSON 值为 `"TASK_STATE_INPUT_REQUIRED"`(`Refs/a2a/docs/specification.md:1219`;`a2a.proto:201`;`a2a-go/a2a/core.go:294`);激活头为 `A2A-Extensions`(`specification.md:3313-3331`;`docs/topics/extensions.md:170-180`;`a2a-go/a2a/svcparams.go:23`);方法名为 `SendMessage`(`extensions.md:193`)。
- `a2a-go` 的 `a2acompat/a2av0` 会把旧的 `x-a2a-extensions` 映射为新头名(`conversions.go:32-62`),并做 Task 状态的新旧映射(`conversions.go:64-70`)。
- `Message.Metadata` 与 `Task.Metadata` 在 v1.0 中均保留(`a2a-go/a2a/core.go:211-212,356-357`)。**x402 的 metadata 键与线协版本无关,可以原样承载。**
- `a2a-go` 服务端对 `required: true` 的扩展强制检查:请求未激活时直接返回 `ErrExtensionSupportRequired`(`a2asrv/intercepted_handler.go:328-340`)。这一行为影响是否把 x402 声明为 required,见 §4.7。

### 4.3 时序对照

现状(经中继,两次交互):

```
A(daemon) --delegate(ix1, TaskDoc)--> hub relay --> B(daemon)
B: Price>0, 无 Payment → 结果(ix1){status:PAYMENT_REQUIRED, payment_required} + 收据 → relay → A
A: awaitQuote 验收据 → pickRail → 新 ix2 → Authorize(opt, ix2)
A --delegate(ix2, TaskDoc, Payment)--> relay --> B
B: POST hub/x402/settle{paymentPayload} → 成功 → Invoke → 结果(ix2){paid{…receipt}} → A
A: recordSettlement 验 hub 收据 → 上链
```

目标(a2a-x402 Standalone,单个 Task;daemon 之间端到端加密):

```
本地 agent --A2A SendMessage--> A(daemon, 127.0.0.1) ==E2E==> hub relay ==E2E==> B(daemon) → B 的本地 agent/provider
B: 该 skill 标价 → Task(t1).status = INPUT_REQUIRED,
   metadata{x402.payment.status:payment-required, x402.payment.required:{x402Version:2,resource,accepts:[anet-credit…]}}
   (B 以自身身份签这条状态更新,并记下 t1 → requirements)
A: 验 B 的签名 → 按本地付费策略决定:
   (a) 策略内:A 作为签名服务 Authorize(opt, bind(t1)) → 以 Message{taskId:t1, metadata{payment-submitted, x402.payment.payload}} 发回
   (b) 超出策略:把 INPUT_REQUIRED 原样交给本地 agent 或运维;拒付时发 payment-rejected
B: 取出 t1 的 requirements → 核对 payload(scheme/network/payTo/amount/绑定)→
   POST hub/x402/settle{paymentPayload, paymentRequirements} → hub 验签、扣款、签收据
B: Task(t1) → WORKING/COMPLETED,metadata{payment-completed, x402.payment.receipts:[…]}
A: 验 hub 收据 → 上链 → 通过 A2A 交给本地 agent
```

其中"B 核对 payload"一步在现有代码中不存在,见 D1。

### 4.5 anet-credit 作为自定义 x402 scheme

- **保留 `anet-credit` scheme 名**。理由已写在代码中:`exact` 在链上移动代币,`anet-credit` 是托管账本记账,客户端必须能区分(`payment.go:50-55`)。
- **需要改动的部分**:
  1. network 字符串符合 CAIP-2(D4)。改动牵涉已签名的 `Authorization.Network`(`payment.go:149`)、`Voucher.Network`、`Receipt.Network`,以及跨 hub 路由对 `"hub:"` 的解析(`federation.go:748`)。这是 ANetCore / ANet / ANetHub 三仓的线协变更,需要契约测试与版本过渡 [推断]。
  2. `extra` 中写明托管性质与完整 hub AID,例如 `{"custodial":true,"hub":"<完整 AID>","decimals":0}` [建议]。
  3. facilitator 接口补 `paymentRequirements`,并由 hub 核对内层 Authorization 与 requirements 一致(同时修复 D2)。
  4. `/supported` 补 `extensions`、`signers`(`signers` 可给出 hub AID 及其 KEL 地址)[建议]。
  5. `payload` 目前是 base64 的 CoreDet-CBOR(`pay.go:192-196`)。若要向上游提交 scheme 规范("贡献而非竞争"),需要一份独立的 scheme 文档,写明 payload 编码、签名算法(Ed25519 + KERI 式 KEL)、nonce 与窗口语义、托管声明 [建议]。
- **托管差异必须写进 scheme 文档**。链上 facilitator 不持有资金;anet-credit 的 facilitator(hub)就是托管方(`facilitator.go:21-28`)。

### 4.6 谁签名:daemon 作为签名服务,并需要付费策略

- 规范允许客户端 agent 把签名交给"designated signing service or wallet"(`spec :124`)。anet 的节点私钥不离开 daemon(`PaymentSeam` 设计,`module.go:76-95`),所以本地 daemon 就是签名服务。
- 标准的 a2a-x402 客户端库只会用自己的钱包签 `exact`,签不了 `anet-credit` [推断]。因此本地 127.0.0.1 A2A 面需要二选一:
  - (a) daemon 在策略范围内代为付款,本地 agent 只看到 `working` / `completed` 和 receipts;
  - (b) 把 `input-required` 交给本地 agent,agent 回 `payment-submitted` 时可以不带 `payload`,由 daemon 按所选 `accepted` 补签;或者 agent 调用现有的 `x402-authorize` 取得 payload(`control_api.go:1026-1068`)。
  [建议] 两者都支持,默认 (b)。(a) 需要运维显式配置上限。
- 付费策略目前不存在(D7)。需要的配置包括:单笔上限、周期上限、收款方允许列表、是否允许自动付款;全新安装默认全部为 0 或关闭。

### 4.7 AgentCard 声明与 `required`

- 规范建议 `required: true`(`spec :33-35`)。a2a-go 会拒绝所有未激活该扩展的请求,免费 skill 也不例外(`intercepted_handler.go:328-340`)。
- [建议] 同时有免费和收费 skill 的 agent 声明 `required: false`;全部收费的 agent 才用 `true`。官方公开 agent 和工具按决策 3 免费开放,应声明 `false` 或不声明。
- 声明代码应放在 `module/x402` 内,由内核通过 `Payer` 询问是否声明、如何声明,这样 `no_x402` 构建的卡片不会出现该扩展,符号数判据仍然成立(`ANet/.github/workflows/ci.yml:141-155` 以 `module/x402` 为匹配模式)[建议]。

### 4.8 Embedded 流(AP2)

规范对两种流程的要求是 SHOULD(`spec :39`)。[建议] 现阶段只实现 Standalone。客户端收到 `payment-required` 但没有 `x402.payment.required` 时,按 Embedded 处理,回 `payment-rejected` 并附"unsupported flow"说明,不去猜测 AP2 结构。

## 5. 缺陷与差距

每项给出位置、行为、影响、发现方式。以下均为阅读代码所得,**未运行复现**(本机无 Go 工具链)。

### D1 提供方结算时不核对授权条款(relay 路径)

- **位置**:`ANet/internal/daemon/capability.go:350-372`;`ANet/module/x402/x402.go:236-260`;`pay.go:205-235`。
- **行为**:提供方把收到的 `paymentRaw` 原样交给 hub 的 `/x402/settle`,只检查 `st.Failed`。不比较 `auth.PayTo` 是否等于本节点 AID,不比较 `auth.Amount` 是否不低于 `price`,不比较 `auth.InteractionID` 是否等于当前 `interactionID`,也不比较 `st.Amount` 与价格。hub 不知道价格,按授权里写的金额和收款方记账(`facilitator.go:198-268`)。
- **影响**:付款方可以对 100 credit 的能力签 1 credit 的授权,或把收款方写成第三方,提供方仍会执行。`TestAnAuthorizationIsBoundToItsInteraction`(`x402_test.go:120-163`)只证明授权**带有**交互 id,没有测试任何一方**检查**它。按 a2a-x402 的 merchant 职责(`spec :140`)和安全要求(`spec :478`),这一核对属于 merchant。
- **发现方式**:阅读 `tryCapabilityPaid` 与 `settle` 的调用链,并在 `internal/daemon/*_test.go`、`module/x402/*_test.go` 中确认没有少付或错付的用例。

### D2 hub 网关核对未签名的 `Accepted`,结算已签名的 `Authorization`

- **位置**:`ANetHub/internal/aghub/gateway.go:310-321`(只看 `pp.Accepted.PayTo/Amount`);`facilitator.go:520-565`(`decodeAuth` 不比较 Accepted 与 auth 的金额和收款方);`facilitator.go:142-330`(按 `auth.Amount` 付给 `auth.PayTo`);`gateway.go:333,357-375`(`issueVoucher` 的 `Amount` 取 `price`,`PayTo` 取路径中的 `aid`)。
- **行为**:买方构造 `Accepted{PayTo:卖方, Amount:价格}`,内层 Authorization 签成 `{PayTo:卖方或第三方, Amount:1}`。网关的检查通过;hub 结算 1 credit;凭证却写明全价、收款方为卖方。卖方兑付时检查 `v.Amount >= want`(`voucher.go:258`),同样通过。
- **影响**:可以少付,也可以把款付给第三方,卖方照常干活。`TestTheGatewayWillNotSellBelowThePublishedPrice`(`gateway_test.go:215-266`)用的 `signedPayment` 让 Accepted 与 Authorization 总是一致(`gateway_test.go:269-296`),所以这条路径两侧测试都为绿。这正是 CLAUDE.md 所说"fake 只实现快乐路径"的情形。
- **发现方式**:对照网关检查的字段与结算实际使用的字段。
- **与目标流程的关系**:x402 规定 `/settle` 须带 `paymentRequirements`,由 facilitator 核对 payload 与 requirements(§3.2)。补上该字段并让 hub 核对,可以同时修复 D1 的 hub 侧部分和 D2。merchant 仍需自行核对任务绑定,因为 hub 不知道任务。

### D3 relay 载荷为明文,hub 能读到任务内容和付款对象

- **位置**:`ANet/internal/daemon/transport.go:40-46`(`payload` 为 base64 明文 CBOR);`ANetHub/internal/aghub/aghub.go:915-917`(落库);`server.go:244`(注释写的是"end-to-end verifiable",即可验证,而非保密);`ANetCore/identity/encrypt.go:73,91`(`SealTo`/`Open` 已存在,但 ANet 与 ANetHub 非测试代码无调用点,grep 核实)。
- **行为**:DelegateReq 中的 TaskDoc(目标、`args`)、附件、`Payment`,以及 ResultResp 中的交付物(含 `payment_required`、`paid`),hub 都能读取和保存。
- **影响**:与决策 2"hub 不得看到任务内容"直接冲突。在支付上,报价的 `resource`(`anet:capability/<capID>`,`pay.go:76`)和交付物都会暴露给 hub。
- **发现方式**:追踪 `relaySend → hubTransport.Send → hRelaySend → RelayEnqueue`。
- 端到端加密的方案属于传输面报告的范围。本报告只给出付款相关的要求,见 §6。

### D4 `hub:<aid>` 不满足 CAIP-2

- **位置**:`ANetCore/payment/payment.go:11-15,66`;`ANetCore/anetcid`(`Sum` 返回 CIDv1 dag-cbor 字符串)。
- **行为**:CAIP-2 要求 `namespace [-a-z0-9]{3,8}`、`reference [-_a-zA-Z0-9]{1,32}` [外部]。仓库中的 AID 样例长 59 字符(如 `bafyreicaw2uaernqv2rnhunxgkjwgsxrundhy4o2f2v423i27bk6yjh7ge`),超过 32 字符上限。
- **影响**:代码注释声称的合规不成立。第三方 x402 客户端或 facilitator 如果校验 CAIP-2,会拒收该网络名。当前网内不受影响。
- **发现方式**:比对 CAIP-2 语法与仓库中的 AID 长度。

### D5 facilitator 协议面与 x402 v2 不一致

- **位置**:请求体 `pay.go:214-216`、`facilitator.go:607-610,620-623`、`wire_federation.go:45-47`;`/supported` `payment.go:127-129`、`facilitator.go:590-604`;`PaymentOption.maxTimeoutSeconds` 的 `omitempty` `payment.go:95`;`PaymentRequired.resource` 可省略 `payment.go:72`。
- **行为**:缺少 `paymentRequirements`、`extensions`、`signers`;两个必填字段可被省略。
- **影响**:外部 x402 工具无法直接对接 hub 的 facilitator。缺 `paymentRequirements` 还是 D2 的结构性原因。
- **发现方式**:逐字段比对 v2 规范 [外部]。

### D6 错误原因多为散文,无法填入 `x402.payment.error`

- **位置**:常量定义 `payment.go:410-427`;除 `ReasonInsufficientFunds`(`facilitator.go:207`)和 `ReasonMalformed`(`gateway.go:303`,`redemption.go:403,488`)外,其余常量没有发出点(grep 核实);`SettlePayment` 返回的是 `decodeAuth` 的散文(`facilitator.go:152-156`)。
- **影响**:merchant 无法可靠地把失败原因映射为错误码,只能匹配字符串。
- **发现方式**:grep 常量使用点。

### D7 自动付款没有上限

- **位置**:`internal/mcpserv/mcpserv.go:63-97`(`pay=true`,限制只写在描述中 `:71-74`);`control_api.go:636-648`;`paylink.go:232-253`(`DelegateAndPay` 不设上限,按报价全额付款)。
- **影响**:编码 agent 通过 MCP 设置 `pay=true` 后,可以花光节点余额。与决策 3"默认安全"不一致。
- **发现方式**:阅读 MCP 工具和 `/delegate` 的付费分支。
- 相关事实:新注册即得 100 credit(`facilitator.go:655`),而 daemon 默认接受委派(`config.go:94,108-109`,属于决策 3 的另一个面)。

### D8 hub 的支付代码无法在编译期去掉;网关要求提供方有公网入口

- **位置**:`ANetHub/internal/aghub/{facilitator,gateway,redemption,issuance,witness}.go` 都没有 build tag;hub CI 的 tag 矩阵见 `ANetHub/.github/workflows/ci.yml:28`。网关的可达性要求见 `gateway.go:32-34`,`voucher.go:33-36`。
- **影响**:只做传输的 hub 仍然带着账本、网关和兑付接口。网关和凭证路径针对的是有公网入口的提供方,与目标用户群(笔记本、NAT 后)不符。这条路径也不属于 a2a-x402 流程。
- **发现方式**:grep `//go:build`;阅读网关注释。
- [建议] 冻结网关和凭证路径,不向 A2A 扩展;hub 侧给账本和网关加减法 tag(如 `no_ledger`、`no_gateway`),并同步 hub CI 矩阵。是否下线网关需要产品负责人决定(§9)。

### D9 公开的账本接口向任何人暴露付款元数据

- **位置**:`facilitator.go:632-643`(余额公开);`server.go:1222-1248`(流水公开,`reason` 列为交易号);`redemption.go:429-454`(兑付列表公开)。

- **影响**:决策允许 hub 看到付款元数据,但当前实现把这些元数据公开给了所有人。这是隐私面的差距,不影响正确性。
- **发现方式**:阅读路由与 handler,确认没有鉴权。

### D10 内核 `Settlement` 不能还原完整的 x402 收据

- **位置**:`module.go:263-269`;`x402.go:244-259`。
- **行为**:丢弃了 `payer` 和其他 `extensions`,只保留收据的 base64。
- **影响**:无法直接写出 `x402.payment.receipts` 所需的完整 `SettlementResponse`。影响较小,改接口即可。

## 6. 付款过程中 hub 能看什么、不能看什么(目标)

允许 hub 看到(付款元数据,决策允许):

- facilitator 请求:付款方 AID、收款方 AID、金额、scheme、network、nonce、有效窗口、授权 id;以及 v2 要求的 `paymentRequirements`。v2 的 PaymentRequirements 本身不含 `resource`(§3.2),因此补上该字段不会带出能力或 skill 名称 [外部/推断]。
  - **更正(2026-09-28,[redteam:F1])**:上句只对"字段内容"成立,不能推出"hub 不知道买了什么"。requirements 带收款方与准确金额,而收款方在卡片上公开签名的逐 skill 价格(anet-pricing/v1、ADP 卡片价格表)时,"收款方 + 金额"即可确定所买 skill,也就是报价里的 `resource`;跨 hub 付款时公开发放链的读者同样能做到。A2A-DESIGN §21 第 9 条已如实写明,并提供 `payments.publish_prices=false`(卡片不发布逐 skill 价格,只在 E2E 报价中给出)。
- 结算收据、账本流水、供应量、发放链。

不得让 hub 看到(任务内容):

- `x402.payment.required` 中的 `resource.url/description/mimeType`。它描述的是"买什么",应只存在于端到端加密的 A2A 消息中。**向 facilitator 发送的 `PaymentPayload` 不应带 v2 的可选字段 `resource`** [建议]。
- Task 的目标、Message parts、artifacts、附件、provider 的 evidence。
- `x402.payment.status/receipts` 等 metadata 也随 Message 在端到端加密内传输。hub 通过 facilitator 调用已经知道结算结果,不需要再从 relay 读取。

需要决策的关联性问题 [推断]:

- 现在 hub 在 relay 请求中能看到 `interaction_id`(`transport.go:44`),在结算中也能看到同一个 `InteractionID`(`facilitator.go:177-179`),因此可以把"哪条 relay 流量"和"哪笔付款"关联起来。
- 如果只希望 hub 看到付款而不能把付款与会话对应起来,授权中绑定的应是 `H(taskId ‖ payTo ‖ salt)` 这类派生值,不是原始 taskId;relay 头部也不应带原始 taskId。merchant 可以重算这个派生值来核对,hub 无法反推。

## 7. 链上 scheme(exact / EVM USDC):现在做还是以后做

**现在不做的理由**:

- 按决策 2,所有入网参与者都有本地 daemon、anet 身份和 hub 账户,网内付款用 `anet-credit` 即可闭环 [推断]。
- `exact` 需要 secp256k1 / EIP-712 签名(EIP-3009 `transferWithAuthorization`)[外部],而节点身份是 Ed25519(`payment.go:212`),`PaymentSeam.Sign` 只能签 Ed25519。钱包私钥是另一类秘密,需要新接缝,不能复用 `PaymentSeam` [推断]。
- `exact` 需要可达的外部 facilitator(HTTPS)和链上 gas,测试依赖外网;按 CI 的"hermetic"原则(`ANet/.github/workflows/ci.yml` scenario 段注释),它进不了合并门禁 [推断]。

**后续需要的场景**:

- 非托管结算:hub 不再是托管方,也彻底退出付款路径,与"hub 只是传输"最一致。
- anet agent 作为客户端向网外 A2A merchant 付款,这类 merchant 大多只接受 `exact`。
- 真实货币计价。现在的 credit 只能经兑付和线下约定变现(`redemption.go:18-43`)。

**现在应该做的接缝** [建议]:

- 在 `module/x402` 内建 scheme 注册表。每个 scheme 提供 `Offer(price) → PaymentOption`、`Sign(opt, binding) → payload`、`Verify/Settle(payload, requirements) → SettlementResponse`、`ErrorCode(reason)`。`pickRail` 改为按 scheme 与付费策略选择(当前硬编码为 `anet-credit`,`paylink.go:448`)。
- 用 `anet-credit` 加一个测试专用的假 scheme 证明接缝可用。按 CLAUDE.md,假 scheme 也要实现完整契约(失败、重放、错误码),不能只有快乐路径。
- `exact/EVM` 以后用**加法 tag**(例如 `-tags x402_evm`)实现:把热钱包签名器误编进构建的代价,大于它缺席的代价,符合 CLAUDE.md 对加法方向的判据。CI 需要另加 `optin` 符号检查和 `go test -tags x402_evm ./...`。

## 8. 建议的改造与测试要求

改造(按依赖顺序)[建议]:

1. **修 D1、D2**(与 A2A 无关,当前实网即可触发):merchant 核对 `PayTo == self`、`Amount >= price`、`InteractionID == binding`、`scheme/network ∈ 已报价选项`;hub 的 `/settle` 接收 `paymentRequirements` 并核对内层 Authorization;网关用结算金额签发凭证,或在不一致时拒绝。每条都要做 mutation 验证。
2. **扩展 `module.Payer`**:`Settlement` 带出完整 `SettlementResponse`;新增 x402 的 A2A metadata 编解码(`required/payload/receipts/status/error`),代码放在 `module/x402`;内核只处理 `map[string]any`,不 import 模块(K207)。
3. **merchant 状态**:taskId → 已开 requirements(含过期时间),持久化到证据链或 interactions 存储,重启后能恢复。`receipts` 保留完整历史。
4. **客户端付费策略**:单笔、周期、收款方允许列表;默认关闭自动付款;MCP `pay=true` 受策略约束;超出策略时对本地 agent 呈现 `input-required`。
5. **协议面对齐 v2**:`/supported` 补 `extensions`、`signers`;`resource` 与 `maxTimeoutSeconds` 必填;hub 发出错误码;network 改为 CAIP-2 形式(三仓联动,需要版本过渡)。
6. **AgentCard 声明**:v0.2 URI;`required` 按 skill 构成决定;激活头同时兼容 `A2A-Extensions` 与 `X-A2A-Extensions`(a2a-go 的 `a2av0` 已提供映射)。
7. **网关与凭证**:冻结;hub 侧加减法 tag。
8. **端到端加密**落地后,补一项断言:hub 的 `relay_message.payload` 中不出现 `x402.payment.required` 的 `resource` 字段和任务文本。

- 契约测试:x402 v2 字段名(扩展现有的 `TestTheX402ObjectsKeepTheSpecFieldNames`,`payment_test.go:183-208`);a2a-x402 的 metadata 键和状态值;`paymentRequirements` 在 daemon、hub、federation 三方的请求体中都出现。
