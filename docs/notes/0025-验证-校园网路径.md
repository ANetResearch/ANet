## 2. 验证明细

最近一次偏移 dmax +7.8 ms、cmax +2.8 ms,误差按 ±10 ms 计);端到端 = 请求方存储里 `created_at` → `state_at`(同一时钟)。
驱动脚本经 ssh stdin 送到主机上执行,令牌只在主机上读、经进程替换的头文件交给 curl,不进 argv,不出主机。

### 2.3 p2p 与回落 hub(首轮 2/4,修复后 3/4)

1. **通过** d4a → d3a 走直连:d4a 的 anetpeer 记 `delivered … → d3a`,委派 16–66 ms 到达。
2. **通过** d3a → d4a 拨号被 cmax 的 ufw 丢弃(SYN 无应答,不是 RST):anetpeer 8 s 后记 `dial tcp 10.253.20.9:47431: i/o timeout`,
   daemon 的 p2p 发送在 3 s 截止(`module/p2p/p2p.go:101-103` 默认 `dial_timeout_ms`),日志
   `transport p2p: context deadline exceeded (falling through; hub is carrying delivery)`(只在状态变化时记一行),
   同一信封改经 hub 送达,内容与收据都正确。这是预期行为。
3. **失败 → 已修(N2)** 回落的代价在**每一条**消息上重复:reach 只看 rendezvous 有没有地址,拨不通的地址永远答"可达",
   dmax→cmax 的每条消息都先付 3 s。修复后(`32b63c1`)拨号失败的地址在窗口内答不可达:

   | 轮次 | d3a → d4a 调用(依次) | 说明 |
   |---|---|---|
   | 第 2 轮 | 3709 → 139 → 3599 → 184 ms | 首次失败开 30 s 窗口;窗口内 139/184 ms 直接走 hub;窗口到期的那次重试再付 3 s,窗口翻倍为 60 s、2 min |
   | 第 3 轮(最终构建,全新节点) | 3459 → 3900 ms;文本 T2 委派 829 ms、end 126/151 ms | 同上(两次调用间隔超过 30 s) |

   窗口内文本任务 d3a→d4a:委派 766/829 ms、回复 54/63 ms、end 246/271 与 126/151 ms(首轮 3.1–3.5 s)。
4. **失败,记录(N3)** 单向可达时出现重复投递:d4a→d3a 的委派经 p2p 16–48 ms 就进了 d3a 的库,但 d3a 在回 ack 之前
   先同步发送回答(回答走 d3a→d4a,要付 3 s),ack 回到 d4a 时它的 3 s 发送截止已过,于是判 p2p 失败、把同一委派经 hub
   再发一遍;d3a 日志 `ix_… redelivered; re-sending the answer we already signed`,回答也发两次。首轮 C1put、C1get、
   T1 的 end、x402 付款各出现一次(d3a `redelivered=2`、`receive: duplicate` 1 次;d4a 3 次 `falling through`)。
   SI-10 保证只处理一次,结果正确,但流量翻倍、时延加倍。N2 修复后只在窗口到期的那次重试上出现(第 2 轮 R2-C1put
   3798 ms 一例;同轮窗口内 280 ms、第 3 轮 301 ms 都无重复,两边 `redelivered=0`)。根因与处理见 §4 N3。
