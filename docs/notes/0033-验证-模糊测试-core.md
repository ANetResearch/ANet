最重要的一条是 **F1(identity,高)**:Replay 把紧挨在 rot 之前那个事件的 next_digest 当作预轮换承诺,
而 ixn/drt 只需当前密钥签名。偷到当前密钥的人可以先追加一条 drt 把"下一把密钥"换成自己的,再用被盗密钥签 rot
轮换过去——正是预轮换要防的接管。`FuzzReplayProgram` 用 12 秒找到。

红队 F34(KEL 里错误长度密钥使 ed25519.Verify panic)确认已修:`FuzzReplayProgram` 的程序专门生成 0–31 字节
和双键的密钥放在 icp/rot/drt 各位置,`FuzzUnmarshalKEL` 喂原始字节,两者共 155 万次无 panic。同一类问题在另一个
入口还在:`aobj.Verify`(F2),5 秒被找到。

## 2. 方法

**目标形式。** 每个 `FuzzXxx(f *testing.F)` 与被测包放在一起(`<包>/fuzz_test.go`)。普通 `go test` 下只跑种子与
`testdata/fuzz/` 下的回归语料,16 个包合计多出不到 1 秒。

**种子。** 取现有金标向量与测试夹具:VEC-SEALED-1 信封及其解密后的明文、`identity.SuiteController()` 的 KEL、
golden 包里 DelegateReq/ResultResp/Receipt/Review/Authorization/Voucher/HeadAttestation 的构造方式、
`a2acard/testdata/golden-card.json` 与测试里的 `baseCard`、ADP-GV-1 形状的卡、AET/TSIR 的 CID 向量、agent-uri 的
AU-* 接受向量。fuzzer 从这些合法结构附近变异。

**重签名。** 变异过的签名对象几乎不会保持有效签名,只喂字节的目标到不了验签之后的检查。所以凡是"解码 → 验签 →
绑定检查"的入口,目标都带一个开关:解码出的对象先用固定身份重新签名再验证。固定身份是套件身份
(`identity.SuiteController()`),或它按承诺轮换一次之后的状态;两者都由公开种子派生,各 fuzz 进程一致。这样绑定与
结构检查在"字段任意、签名有效"的输入上跑,"验证接受了不该接受的东西"才可能暴露。

- seal 的 `FuzzOpenInner` 按同样思路处理:对变异后的明文字段表按 Open 将要构造的 preimage 重签,再用接收方公钥
  自行 HPKE 加密。于是 VerifyInnerSig(含轮换宽限分支,种子里带一份已轮换的 KEL)与 VerifyInnerKeys 在任意内层
  字段上运行。
- `identity.FuzzReplayProgram` 不喂 KEL 字节,而是喂一段"程序",每 4 字节一步:事件类型、密钥形状与长度、
  next 摘要、签名者,以及 seq/prev/AID/签名的篡改位。按程序构造 KEL 并真实签名,再与一个按规则直写的模型比对。

**性质断言。** 每个目标都有,见 §3 表的"性质"列。主要几类:

- 不 panic、不超时:tsir 的求值与 glob 包了 2 秒看门狗,超时即 panic,由 fuzzer 记录输入。
- 往返:解析成功后重新编码、再解析得同值,再编码字节相同。适用于 coredet、各 Unmarshal*、ParseOuter、agent-uri
  规范形、JCS;另有 adp 卡 JSON 往返后 pre-image 不变,TaskDoc 往返后 CID 不变。
- 验证通过,则签名者等于声明者,且签名确实出自声明的 key state(用 `ed25519.Verify` 独立复核)。绑定字段逐项复核:
  收据的 provider/requester/interaction/request/结果哈希、interlock、授权的 payer 与有效期窗口(用大整数计算)、
  凭证的 nonce 与有效期、密钥集的 AID/规范编码/有效期。
- 模型比对:KEL 回放结果与模型一致,包括有效性,以及每个 key state 的密钥、状态和委托密钥。另外断言 KEL 的每个
  前缀都能回放;`ExtendsKEL` 对自身、前缀与回滚的判定正确;带 ReplayCache 与不带的结果一致。
- 与第二实现比对:
  - a2acard 的 JCS 输出与 `encoding/json` 读到的值相同;
  - 被 Verify 接纳的卡,`encoding/json` 读出的 name、中继接口 tenant、anet-card aid、技能,与 Verify 读到的相同。
    daemon、hub、a2a-go 都用结构体读存储的字节,这条性质保证它们看到的就是被检查过的内容;
  - publish form 的卡两种 payload 相同,签名后仍是 publish form,自签以 proto-stripped 形式验证通过;
  - 新 glob 实现与原递归实现在星号不多于 4 个的输入上结论相同。
- `a2acard.FuzzVerify` 喂整张已签名的卡:被接纳的卡,至少一个签名覆盖的 payload 必须是夹具亲手签过的。

**执行。** 每个目标单独执行 `go test -run '^$' -fuzz '^FuzzX$' -fuzztime=5m -fuzzminimizetime=10s -parallel=2`,
按顺序跑,同一时刻只有一个 fuzz 进程。`-fuzzminimizetime` 调到 10s 的原因:默认 60s 时,每个新的"有趣"输入都要
最小化一分钟,agent-uri 第一次试跑的 100 秒里只执行了 3.3 万次,见 §6。语料缓存用 `-test.fuzzcachedir` 指到
工作树外的临时目录,首轮各目标从空缓存开始,复跑时接着用。崩溃输入由 go 写到 `testdata/fuzz/FuzzX/`,保留为
回归种子。

**覆盖增长。** 对每个目标,量两次它所在包的语句覆盖率(`-coverpkg=<该包>`):模糊前只跑种子与 testdata 语料;
模糊后把缓存语料临时拷进 testdata 再跑一次,随即删除。表中记为"前 → 后"。分母是整个包:包里本目标不触及的代码
(例如 identity 的 Controller、加密与缓存,a2acard 的 Sign 与 JWKS)也算在内,所以绝对值低不等于入口没被打到。
"新增有趣"指本轮加入语料的覆盖扩展输入数与语料总数。

**每个发现的处理顺序:** fuzzer 自动最小化输入 → 定位根因 → 修复 → 写普通单测回归 → 用文件备份去掉修复,确认单测
与回归语料变红 → 还原 → 对该目标再跑 5 分钟确认。

## 4. 发现与修复

根因处的行号指 `integ/round6`(ANetCore `7b43f46`)。

### F1 identity:预轮换可被当前密钥绕过(高;fuzz 发现)

- **发现。** `FuzzReplayProgram` 试跑第 12 秒。回归语料 `identity/testdata/fuzz/FuzzReplayProgram/c1b14e0ea6748460`
  是 icp(承诺 D)→ ixn(另一个摘要)→ rot(新密钥的摘要为 D)。模型判有效,Replay 却拒绝。
- **根因。** `identity/identity.go:442` 用 `priorNextDigest(kel, i)`(:518)取紧挨在 rot 之前那个事件的
  next_digest。ixn/drt 只需当前密钥签名,却能改写这个"承诺"。
- **影响。** 这条性质的反面才是攻击:偷到当前密钥 k0 的人追加 drt(或 ixn),把 next_digest 写成自己密钥的摘要
  H(ka),再用 k0 签一条 rot 轮换到 ka,Replay 接受。身份被接管,所有者预承诺的 k1 失效,正是包注释里
  "a stolen current key cannot rotate to an attacker key"要防的情形。反向的后果:所有者的合法 rot,只要跟在一条
  摘要不同或为空的 ixn/drt 后面就被拒;早先 Delegate 不带摘要时正是这样,那次修复改的是 Delegate,没有改规则。
- **修复。** replay 记住最近一次建立事件(icp/rot)的 next_digest(`committed`),rot 必须与之匹配,ixn/drt 上的
  摘要不再算承诺。Restore 改用同一个承诺(`committedNextDigest`)。Delegate 仍在 drt 上写同一摘要,旧版验证者
  照样接受下一次 Rotate。
- **兼容。** 合法 Controller 产生的 KEL,修复前后结论都不变。新拒绝的只有"rot 匹配的是中间 ixn/drt 改写的承诺"
  这一种;新接受的是"中间 ixn/drt 摘要不同,但 rot 匹配建立事件"这一种。新旧版本并存期间,旧版验证者仍会接受
  前一种,升级需要让 daemon 与 hub 都拿到这一版 ANetCore。
- **回归。** `identity/prerotation_internal_test.go`,两个用例:
  - `TestAStolenCurrentKeyCannotRecommitThroughADrtOrIxnAndRotate`:drt、ixn 两种重承诺都被拒,攻击者签的对象
    不能通过 VerifyObject;
  - `TestARotToTheCommittedKeyReplaysAcrossAnIxnOrDrtWithAnotherDigest`。
  去掉修复,两个用例和回归语料都变红。
- **复跑。** 修复后,`FuzzReplayProgram` 5 分钟 28.8 万次、`FuzzUnmarshalKEL` 5 分钟 126 万次,无发现。

### F2 aobj:Verify 对错误长度公钥 panic(中;fuzz 发现)

- **发现。** `FuzzEnvelopeVerify` 第 5 秒,最小化为 1 字节公钥加 64 字节签名。回归语料
  `aobj/testdata/fuzz/FuzzEnvelopeVerify/2690a52830d16b2d`。
- **根因。** `aobj/aobj.go:54` 直接调用 `ed25519.Verify(pub, …)`,只检查了签名长度。与红队 F34 同类,入口不同。
  目前 ANet、ANetHub 没有调用方(grep),属于潜在问题,但这是导出函数,文档说公钥可能来自对象发送方。
- **修复。** 先检查公钥是否 32 字节。
- **回归。** `TestVerifyRefusesAWrongLengthKey`,覆盖 0/1/31/33/64 字节。去掉修复即红。
- **复跑。** 5 分钟 428 万次,无发现。

### F3 agent-uri:查询里的非法 UTF-8 使不同 URI 共用规范形(中低;fuzz 发现)

- **发现。** `FuzzCanonical` 第 34 秒:`Agent://0?a%800=`。回归语料 `agenturi/testdata/fuzz/FuzzCanonical/39d63fdd489bb561`。
- **根因。** 查询键值经百分号解码后得到非 UTF-8 字节。Parse 照收;Serialize 按 rune 迭代,把非法字节变成 U+FFFD,
  再编码成 `%EF%BF%BD`。结果 `?k=%FF` 与 `?k=%FE` 的规范形相同,Equals 为真。规范形是"唯一可签名、可比较的形式",
  这里却让两个不同的值相等。标签走 decodeComponent,在 `agenturi/agenturi.go:167` 检查了 UTF-8;查询走的
  decodeQ(:175)漏了同一检查。
- **修复。** decodeQ 同样检查,不合法时报 BAD_UTF8。
- **回归。** `TestQueryInvalidUTF8IsRejected`。去掉修复即红。
- **复跑。** 修复后 5 分钟 618 万次,无发现。

### F4 agent-uri:KELVIN SIGN 使规范形不是不动点(低;审读发现)

- **根因。** foldLabel(:218–237)先做映射(ASCII 小写化、ß→ss、ς→σ、去掉 ZWJ/ZWNJ),再做 NFC。而 NFC 会产出
  映射本该处理的字符:U+212A KELVIN SIGN 规范化后是 ASCII 'K'。于是 `agent://%E2%84%AA` 的规范形是 `agent://K`,
  它自己的规范形却是 `agent://k`,违反 AU-C-08(幂等);Equals 也判 `%E2%84%AA` 与 `k` 不等。
- **修复。** 对 NFC 之后的串做映射,映射后再 NFC 一次。其余输入的规范形不变,AU-* 接受向量全绿。
- **发现方式。** 设计 FuzzCanonical 的种子时审读发现。F3 修复后 fuzz 又跑了 5 分钟、618 万次,没有撞到这个
  三字节序列;已把它加为种子。
- **回归。** `TestKelvinSignFoldsToLowercaseK`。去掉修复即红。

### F5 agent-uri:只含连接符的标签折叠成空(低;审读发现)

- **根因。** 只有 ZWJ/ZWNJ 的标签经 S3 折叠后为空串,Parse 接受,规范形 `agent://` 或 `/ns=` 却无法解析。
- **修复。** rejectCheck 对空标签报 EMPTY_LABEL;三处折叠后的标签都经过它。
- **发现方式。** 与 F4 相同,fuzz 5 分钟未撞到,已加为种子。
- **回归。** `TestLabelOfOnlyJoinersIsEmpty`。去掉修复即红。
- **复跑。** F4、F5 修复后 5 分钟 771 万次,无发现。

### F6 tsir:glob 匹配指数时间(中,潜在;fuzz 发现)

- **发现。** `FuzzGlobMatch` 第 32 秒:模式 `*********************0`(21 个星号)对一个 20 字节串,看门狗 2 秒超时。
  回归语料 `tsir/testdata/fuzz/FuzzGlobMatch/ea20d7aa5f7cff0d`。
- **根因。** `tsir/predicate.go:302` 的 globHelper 在每个 `*`/`**` 处枚举所有切分点并递归,k 个星号的代价是 O(n^k)。
- **影响。** predicate 来自 TaskDoc 的 acceptance 与 scope,TaskDoc 由请求方签名;EvaluateScope 是负向范围的硬闸。
  目前 ANet/ANetHub 不调用 Evaluate,属潜在 DoS。
- **修复。** 改为逐 token 推进"可达位置集合",代价 O(len(pat)·len(s)),语义不变。原递归实现保留在 fuzz 目标里
  作参照,做差分比对;另加 `TestGlobMatchDialect` 固定方言。
- **回归。** `TestGlobMatchIsNotExponential`,包括发现的输入,以及 30 个 `**a` 对 4000 字节。去掉修复后,该测试
  1 分钟超时。
- **复跑。** 5 分钟 535 万次,与原实现差分一致;`FuzzPredicateEvaluate` 另 5 分钟 314 万次,均无发现。

### F7 tsir:Validate 遇到 null 子节点 panic(中低,潜在;审读发现)

- **根因。** CBOR null 出现在 children 数组里时,解码成 nil `*Predicate`;validate(:146)直接 `p.Op` 解引用。

- **回归。** `TestValidateRefusesANullChild`。去掉修复即红。

### F8 seal:Padme 在 math.MaxInt 附近回绕为负(低;边界种子触发)

- **根因。** `seal/fields.go:181` 的 `(n + mask) &^ mask` 在 n > MaxInt − mask 时溢出。消息不可能这么长,所以实际

- **修复。** 这种情况原样返回 n(仍然 ≥ n,且是不动点),文档写明。
- **回归。** `TestPadmeDoesNotWrapNearMaxInt`。去掉修复即红。

### F9 payment:有效期比较在 NotAfter 近 MaxInt64 时溢出(低,失败关闭;审读发现)

- **根因。** `payment/payment.go:264` 的 `now > a.NotAfter+ClockSkew`,以及凭证的同式(:635):NotAfter 接近

- **修复。** 比较差值(`pastWithSkew`/`beforeWithSkew`,用 uint64 差),窗口两端的语义不变。
- **回归。** `TestWindowEdgesDoNotOverflow`,含窗口边缘与 ±MaxInt64 时刻;另把该输入加为 FuzzAuthorization 的种子。

- **复跑。** 两个目标各 5 分钟,共 785 万次,无发现。

## 5. 记录未修

**R1 adp:pre-image 绑不住 2^53 以上的整数(低;审读并用探针确认;修过又撤回)**

- **根因。** `adp/adp.go:201` 的 preimageObject 先把卡 json.Marshal,再 json.Unmarshal 进 `map[string]any`,
  没有 UseNumber,所有数字都成了 float64。jcs.go 里的 json.Number 分支只用于 RawMessage 字段,文件头"保持整数
  原文"的说法对 seq、issued_at 不成立。于是 2^53 以上的相邻整数共用一个 pre-image 和一个签名:seq 为 2^53+1 的
  已签名卡,改成 2^53 后 AdmitCard 照样接受。hub 用卡的 seq 做高水位(card.go:74/653)。
- **修过又撤回。** 曾让 AdmitCard/AdmitTombstone 拒绝超出 ±(2^53−1)(I-JSON 安全整数)的
  seq/issued_at/not_before(4ecd6d2)。ANetHub 全量测试随即 200 处失败:hub 的测试夹具用 UnixNano 作 seq
  (约 1.8e18),而且依赖它在连续调用之间严格递增。于是撤回(d252fcc),只在 preimageObject 注释里写明这一局限。
- **现实影响。** 小。daemon 的卡用 unix 秒作 seq;即使用纳秒,1.8e18 处 float64 的粒度是 256,转发方最多把 seq
  挪动 ±128 而签名不变,而发布方下一张卡的 seq 要大出 1e9 量级,高水位推不过它。
- **两种修法,需要一起定:**
  - 限制在 I-JSON 安全整数:AdmitCard 拒绝更大的值,hub 夹具与所有发布方改用秒或毫秒,且保证同一时刻内递增;
  - 让 pre-image 保留整数原文(preimageObject 用 UseNumber,jcsNumber 再按 ParseUint 处理):偏离 RFC 8785,
    已签发的大 seq 卡在新代码下会验签失败。

**R2 adp:pre-image 的数字与键序不是 RFC 8785**

- **现象。** 非整数用 Go 的 'g' 格式输出:0.00001 成了 `1e-05`,RFC 8785 要求 `0.00001`;1e-7 成了 `1e-07`,
  RFC 8785 是 `1e-7`。对象键按字节序排序,RFC 8785 按 UTF-16 码元排序,两者只在 BMP 以上字符的键上不同。
- **影响。** 同一套 Go 代码签名、验签不会出问题;但另一种实现按 RFC 8785 计算 pre-image 时,扩展里带这类数字或键的
  卡会验签失败,card_cid 也不同。
- **为什么不在这里改。** 改动会改变这类卡的 pre-image。hub 联邦重同步时会再跑 AdmitCard(card.go:653),
  已签发的卡在新代码下验签失败,需要一次带版本号的切换。
- **建议。** 先决定 adp-card 是否严格遵循 RFC 8785;若是,pre-image 改走 a2acard.Canonicalize 这同一份实现。
  FuzzAdmitSigned 的 RFC 8785 差分检查目前只用于不含自由 JSON 的卡。

**R3 delegation:返回的 TaskDoc 字节不全在请求方签名之内**

- **现象。** VerifyDelegateReq 与 VerifyDelegateReqWithKEL 返回的 taskDocBytes,是载荷里携带的原始字节;
  而 TaskDoc 的签名只覆盖 CanonicalPreimage,即去掉 meta、minor、critical 并重新编码后的字节。所以原始字节里可以
  有未签名的 meta、critical,或非规范编码;daemon 用 tdBytes 计算的请求 CID 随之变化,签名却不变。
- **为什么不构成可利用问题。** wire 2 下整个 DelegateReq 在密封信封里,由信封的内层签名认证,中继改不了。
- **遗留。** 函数注释说返回的是"the exact signed TaskDoc bytes",这并不准确。第三方如果只拿 TaskDoc 的签名去
  核对 requestDoc,meta 等内容不受请求方签名担保。未改。

**R4 tsir:glob 的 `**` 会吞掉其后的 `/`**

- **现象。** 因此 `a/**/b` 也匹配 `a/xb`。F6 的重写保持了原语义,差分比对可证。
- **影响。** 对负向 scope,这让匹配更宽,是失败安全的一侧;对 acceptance 里的 artifact 路径,则是更松的一侧。
- **待定。** 是否符合 tsir-spec §3.2,需要规范作者确认。

另:ParseAmount 接受前导零("007")。所有调用方都比较解析后的数值,不构成问题。

## 6. 未能覆盖的部分

- **anetcid。** 只有 Sum/SumRaw,是哈希,没有解码入口,未单列目标;各目标计算 CID 时顺带覆盖。
