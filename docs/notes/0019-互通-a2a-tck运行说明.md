# 0019 · 互通:a2a-tck 运行说明(本机 A2A 接口)

日期:2026-09-27。对应:设计 §17 联调行"a2a-tck 结果记录(不作门禁)",计划 0014 的 B5-03(本包写脚本与说明,
记录跑出来的结果)、B7-01(汇总)。脚本:`scripts/a2a-tck.sh` + `scripts/a2a-tck-plugin.py`。

TCK 版本:a2aproject/a2a-tck `263b9cf`(`/data/projs/anet-dev/Refs/a2a-tck`)。TCK 升级后需重核 §3 的分组。

## 1. a2a-tck 如何对被测服务运行

- **入口**:`run_tck.py --sut-host URL [--transport …] [--level must|should|may] [-- pytest 参数]`,本质是
  `pytest tests/compatibility/`,报告固定写到当前目录下的 `reports/`。`run_sut.py` 用来按 YAML 下载、构建、
  启动一个参考 SUT,与测 anet 无关。
- **发现**:从 `{sut-host}/.well-known/agent-card.json` 取卡片(用 `httpx.get`,**不带任何鉴权头**,非 2xx 时
  整个会话报错),再按 `supportedInterfaces[].protocolBinding`(`JSONRPC` / `HTTP+JSON` / `GRPC`)为每个绑定建
  一个客户端,URL 取接口条目的 `url`。`--transport` 只能在卡片声明的绑定里再筛。
- **鉴权**:TCK 没有任何鉴权选项(无 header 注入参数,也不读 `securitySchemes`)。
- **客户端细节**(影响路由):
  - JSON-RPC 客户端以接口 URL 作 httpx `base_url` 再 `POST "/"`,实际请求是 `…/jsonrpc/`(带斜杠);
    不少用例又用裸 `httpx.post(接口URL)` 发到 `…/jsonrpc`(不带斜杠)。两种路径都会出现。
  - REST 客户端同理,请求是 `…/rest/message:send`、`…/rest/tasks/{id}` 等。
  - 客户端一律发 `A2A-Version: 1.0`;超时:传输客户端连接 5 秒、读 30 秒;裸 `httpx` 调用缺省 5 秒。
- **SUT 行为约定**:`scenarios/*.feature` 按 `messageId` 前缀规定 SUT 的执行器行为(`tck-complete-task` 立即
  完成、`tck-input-required` 置 input-required、`tck-artifact-*` 产生各类产物、`tck-message-response` 直接回
  Message、`tck-stream-*` 按序推流等)。TCK 的参考 SUT 由这些场景生成;被测实现若不按前缀行事,相关用例会失败,
  或因前置任务状态不符而被 TCK 自己 `skip`。
- **结果口径**:MUST 失败即失败,SHOULD/MAY 失败记 xfail;每条要求的状态是 PASS / FAIL / SKIPPED / NOT TESTED。
  兼容率分母去掉 SKIPPED,**NOT TESTED 留在分母里**;TCK 控制台汇总表把 NOT TESTED 也算作 Failed,以
  `compatibility.json` 的 `status` 为准。

## 2. 对 anet 的映射与脚本做了什么

被测对象是"本机接口上的一个远端 agent",`--sut-host = http://<a2a_addr>/a2a/v1/agents/<aid>`,于是 TCK 取的卡片
正是代理卡片 `…/<aid>/.well-known/agent-card.json`;卡片里的两个接口是 `…/<aid>/jsonrpc` 与 `…/<aid>/rest`。

`scripts/a2a-tck.sh` 依次:

1. 解析地址与令牌:缺省读 `<数据目录>/modules/a2a/a2a_addr.txt` 与 `a2a_token.txt`(数据目录 = `--data-dir`、
   `$ANET_DATA_DIR` 或 `~/.anet`);可用 `--addr`、`--token-file` 覆盖。**不接受命令行上的令牌**。
2. 建 venv(缺省 `<ANet>/../.venv-tck`;有 `uv` 用 `uv`,否则 `python3 -m venv`;系统缺 ensurepip 时建无 pip 的
   venv,再用系统 pip 以 `--python <venv>` 只往 venv 里引导 pip),按 TCK `pyproject.toml` 的依赖列表安装。
   从不往系统 Python 装包。
3. 把 TCK 的 `pyproject.toml tck tests specification` 复制到结果目录下的快照里跑(不往共享检出里写
   `reports/`、`.pytest_cache`、`__pycache__`),跑完删除快照(`--keep-src` 保留)。
4. 预检(`preflight.json`):无令牌取卡片应得 401;带令牌取卡片;两个绑定都在且与卡片同源;
   `pushNotifications`/`extendedAgentCard` 未声明;`securityRequirements` 存在;JSON-RPC 不带斜杠与带斜杠两条
   路径对不存在的任务回 `-32001`;REST `GET /tasks/{不存在}` 回 404;`GET /a2a/v1/agents` 列出该 AID。
   必需项不过则不跑 TCK,退出码 2。
5. 以 pytest 插件(`-p anet_tck_plugin`)运行 TCK:
   - 给发往被测端口的回环地址(卡片主机、`127.0.0.1`、`localhost`、`::1`)的每个 httpx 请求补
     `Authorization: Bearer <令牌>`(已有该头则不动)。令牌只从文件读,不进 argv、环境变量与报告。
   - 按 §3 跳过不适用分组,并把跳过清单写入 `anet-skips.json`。
   - `--jsonrpc-slash-fix auto`(缺省):仅当预检发现接口不接受 `…/jsonrpc/` 时,在客户端把它改写为
     `…/jsonrpc`,并在 `run.json` 记 `jsonrpc_slash_fix=applied`——这是接口问题(§4 第 2 条),改写只为让其余
     用例有结果,不代表通过。
6. 生成 `run.json` 与 `summary.md`(§5)。TCK 用例失败不影响退出码(`--strict` 时透传 pytest 退出码);只有
   环境/接口不可用才非零退出。

用法:

```bash
# 列出分组(不需要 SUT)
scripts/a2a-tck.sh --list-groups

# 典型:joint-a2a 环境里的请求方 daemon(JOINT_KEEP=1 留着进程),对端 AID 已知
scripts/a2a-tck.sh --aid "$PEER_AID" --data-dir /tmp/joint-a2a-$(id -u)/run/req/.anet --out /tmp/tck-$(date +%s) --label "joint-a2a $(git rev-parse --short HEAD)"
# 或者由联调脚本代跑:JOINT_A2A_TCK=1 bash scripts/joint-a2a.sh,记录在 $J/run/tck(对端由脚本的 responder 作答)

# 只测协议面(不需要对端作答),只跑 MUST,只走 JSON-RPC
scripts/a2a-tck.sh --aid "$PEER_AID" --scope protocol --level must --transport jsonrpc

# 透传 pytest 参数
scripts/a2a-tck.sh --aid "$PEER_AID" -- -k "error_codes or problem_details" -x
```

前提:daemon 在跑且 module/a2a 已启用;`--aid` 是本机已知的远端(有代理卡片);对端把本机放进允许名单
(否则任务直接 `rejected`,`closed` 缺省,X2)。**副作用**:除错误路径外,每条 TCK 消息都是一次真实委派,经 hub
发往对端,每个用例、每个传输各一次。只对测试用 agent 跑,不对生产或付费 agent 跑(付费能力会进入
`input-required` 的付款流程;agent 档支出上限缺省 0,不会自动付款,但仍会产生交互与证据)。

脚本在本工作树上用一个只模拟 URL 形状与鉴权的假服务验证过:无 401(令牌注入生效)、跳过分组与记录、
斜杠改写的 auto 判定、报告与摘要生成;结果目录与报告中不含令牌。

## 3. 适用 / 不适用分组

### 3.1 不适用(脚本永远跳过,报告记 SKIPPED,不计入兼容率分母)

| 分组键 | 范围 | 理由(设计出处) |
|---|---|---|
| `grpc` | `tests/compatibility/grpc/`、各文件中的 gRPC 用例、`GRPC-*`、参数化用例的 grpc 传输 | module/a2a 只提供 JSON-RPC 与 HTTP+JSON,不导入 `a2agrpc`(§11.1);代理卡片只声明这两个绑定。`--transport` 也不接受 grpc |
| `push` | `PUSH-CREATE/GET/LIST/DEL/DELIVER-*`(`test_push_notifications.py`) | 推送 4 个操作一律 `PushNotificationNotSupported`,卡片 `pushNotifications: false`(§11.3、§11.5) |
| `extended-card` | `CARD-EXT-001`、`CARD-EXT-002` | GetExtendedAgentCard 不支持,卡片不声明 `extendedAgentCard`(§11.5) |
| `message-response` | `test_artifacts.py::TestMessageResponse`(`tck-message-response` 场景,DM-MSG-001) | 经本机接口的每次发送都是一个交互,task id 即 interaction id(§2"本机 A2A 接口形态"、§11.5),SendMessage 总是回 Task |

以下"不支持时应报的错"**仍然运行**,它们检验的正是 anet 的拒绝形态:CORE-CAP-001(推送 → -32003 / HTTP 400
`PUSH_NOTIFICATION_NOT_SUPPORTED`)、JSON-RPC 与 HTTP 状态码映射里的推送用例、CORE-CAP-003(GetExtendedAgentCard
→ `UnsupportedOperationError`)。

### 3.2 TCK 按卡片自行跳过、或没有自动化用例

| 范围 | 原因 |
|---|---|
| CORE-CAP-002 与 "-32004 / HTTP 400:不支持流式" | 代理卡片声明 `streaming: true`(§11.3) |
| CORE-CAP-004 必需扩展缺失 | 卡片不声明 TCK 的 `urn:a2a:tck:required-extension`;x402 扩展不设为必需(§8.7) |
| CARD-SIGN-*、AUTH-*、VER-CLIENT-*、VER-SERVER-001、BIND-EQUIV-* 等 | TCK 标 `not-automatable` 或没有用例,报告为 NOT TESTED(卡片签名由 ANet 契约测试以 a2a-go 交叉验证,§17 ANetCore 行) |

### 3.3 适用,但需要对端真实作答(分组键 `needs-peer`;`--scope protocol` 时跳过,报告为 NOT TESTED)

凡发出非错误路径消息的用例:参数化的 CORE-SEND-001、CORE-STREAM-001..003、CORE-EXECUTION-MODE-001/002、
CORE-MULTI-001/001a/002/002a/003;`test_artifacts`、`test_data_model`、`test_task_lifecycle`、`test_task_history`、
`test_stream_ordering`、`test_multi_stream` 全部;`test_transport_behavior` 的 JSON-RPC/REST 格式、服务参数、流式
各类;VER-SERVER-003;HTTP 2xx 用例;JSON-RPC SSE 格式与 SubscribeToTask 首事件。

它们的结果取决于对端,解读时分两层:

- **需要对端及时作答**:阻塞 SendMessage 等到终态或中断态才返回(§11.5 [C22]),而 TCK 裸调用只等 5 秒、客户端
  读 30 秒。对端不在时限内回复,记为超时失败。
- **需要 TCK 场景语义**:断言特定产物/状态的用例(产物类型、`input-required` 前置任务、按序流事件、历史)
  要求对端按 `messageId` 前缀行事。anet 的对端看不到场景前缀,除非客户端 messageId 随消息送达(§11.5 把它存进
  `message.metadata["a2a.messageId"]`)且对端的自动回复夹具按前缀作答;否则这些用例或失败、或因前置状态不符被
  TCK 自己 skip(NOT TESTED)。此外 anet 的产物由内核生成(`anet.reply`、交付物、`anet.receipt`、附件,§11.5),
  与场景期望的产物不一一对应。

这样的夹具是 `scripts/a2a-tck-responder.py`(0023 加):在 provider 一侧经控制面(`/tasks/list`、`/tasks/reply`)
按 messageId 前缀作答,`python3 scripts/a2a-tck-responder.py <provider 控制口> <provider 的 control_token.txt>`,
代替 a2aprobe 的 responder。它补上 input-required 前置状态等用例。客户端的 messageId 在 provider 看到的历史里是
请求方消息的 `metadata["a2a.messageId"]`(redteam F33 之后,消息自身的 messageId 是信封 id;夹具两处都认,0029 §4.2)。
0017 Q32 之后,TCK 复用 messageId 与请求方去重相撞只剩一种情形:同一任务内的追问复用同一 messageId,被当作重试
(CORE-HIST-005/006,0029 §4.3);0023 §4.3 的 18 个跳过已不再出现。

### 3.4 适用,只检验接口本身(任何对端都应通过)

卡片(发现、结构、协议声明、BIND-FIELD-001、缓存头 CARD-CACHE-*);对不存在任务的 GetTask / CancelTask /
SubscribeToTask 与带不存在 taskId 的 SendMessage(CORE-GET-002、CORE-CANCEL-003、CORE-MULTI-004、STREAM-SUB-004);
ListTasks 按新 contextId(CORE-LIST-001..005);错误结构(CORE-ERR-*、JSONRPC-ERR-*、HTTP_JSON-ERR-*、AIP-193、
ErrorInfo);错误码与 HTTP 状态映射;版本(VER-SERVER-002);Content-Type;CORE-SEND-003;客户端侧检查
(JSONRPC-SVC-001、HTTP_JSON-URL-*、HTTP_JSON-QP-001)。

## 4. 对 module/a2a 的接口要求(由 TCK 的行为推出)

1. **卡片保持需 Bearer**(§11.2、X5),不为 TCK 放开。TCK 取卡片不带鉴权,由脚本插件补头解决。代理卡片
   `supportedInterfaces[].url` 须与卡片同一端口的回环地址(`127.0.0.1` 或 `localhost` 均可),否则插件不会给
   它补令牌。Host 白名单须同时接受 `127.0.0.1:<port>` 与 `localhost:<port>`。
2. **JSON-RPC 路由同时接受 `…/jsonrpc` 与 `…/jsonrpc/`,且不用重定向**:TCK 两种路径都发;若用 301/302 把
   一种导到另一种,httpx 跟随时会把 POST 变成 GET。(脚本的 auto 改写只是兜底,并会记入结果。)
3. **中间件产生的错误与 a2a-go 同形**:JSON-RPC 为 error 对象,`data` 数组含
   `google.rpc.ErrorInfo{domain:"a2a-protocol.org", reason}`;REST 为 AIP-193,`details` 含同样的 ErrorInfo,
   `error.code` 等于 HTTP 状态码。具体:
   - `A2A-Version: 99.0`(显式非 1.x)→ JSON-RPC `-32009` / HTTP 400 `VERSION_NOT_SUPPORTED`(§11.4)。
   - 请求体的 Content-Type 既不是 `application/json` 也不是 `application/a2a+json`(两种绑定都接受这两种,可带参数)
     → JSON-RPC 宜回 `-32005 ContentTypeNotSupportedError` error 对象(回裸 415/400 时 TCK 记 skip,不记通过);
     REST → AIP-193 `CONTENT_TYPE_NOT_SUPPORTED`。HTTP 状态两者都是 400(A2A v1.0.1 §5.4,`99bed37` 起;此前 415),
     TCK 的 REST 用例仍期望 415,见 §5。
   - 响应类型:TCK 的客户端发 `Content-Type: application/json`、不发 `Accept`(httpx 缺省 `*/*`),并检查响应
     `Content-Type` 含 `application/json`(HTTP_JSON-SVC-001、HTTP_JSON-ERR-001)。REST 绑定按 `Accept` 协商,
     不区分两种 JSON 类型时跟随请求体类型(设计 §11.4),所以 TCK 得到 `application/json`;注意
     `application/a2a+json` 不含子串 `application/json`,若改成一律回 `application/a2a+json`,这两条会失败。
4. **能力不支持的错误先于任务存在性检查**:推送 4 个操作对任意 task id(TCK 用不存在的 `"t"`)都回
   `PushNotificationNotSupportedError`;GetExtendedAgentCard 回 `UnsupportedOperationError`(-32004 / 400),
   不是 `ExtendedAgentCardNotConfiguredError`、也不是 MethodNotFound。
5. **不存在的任务一律 TaskNotFound**(-32001 / 404 `TASK_NOT_FOUND`),包括 SendMessage 带不存在的 taskId
   (CORE-MULTI-004)。"拒绝客户端指定新任务 id"(§11.5)也应回 TaskNotFound,而不是 InvalidParams。
6. **终态任务**:SendMessage → `UnsupportedOperationError`(CORE-SEND-002,与 C35 一致);CancelTask →
   `TaskNotCancelableError`(CORE-CANCEL-002);SubscribeToTask → `UnsupportedOperationError`(STREAM-SUB-003),
   而不是发一个快照后关闭。taskId 与不匹配的 contextId 同给 → 报错(CORE-MULTI-006)。
7. **去重只在客户端给了 contextId 时生效**:TCK 在一次会话里对不同用例、不同传输复用同一 messageId
   (如 `tck-complete-task-<会话>`)且不带 contextId。若按 `(空 contextId, messageId)` 去重,会把不同用例并成
   同一个任务(阻塞与 `returnImmediately` 两个用例会拿到同一个旧任务)。
   **已决定(0017 Q32),有意偏离**:anet 仍按 (对端, 客户端 messageId) 去重(客户端超时重试说不出 daemon 生成的
   contextId),但只针对非终态任务,命中终态任务时建新任务。带 taskId 的追问复用同一 messageId 仍按重试处理
   (0029 §4.3)。
8. **CORE-SEND-003**:raw part 的 mediaType 不被支持应回 `ContentTypeNotSupportedError`。§11.5 目前把任意 raw
   FilePart 收为附件,此项预期失败。待定:按代理卡片 `defaultInputModes ∪ skills[].inputModes` 检查(缺省或含
   `*/*` 时放行),或列为偏离。交 B6-02 定。
9. **SHOULD/MAY**:卡片响应带 `Cache-Control`(含 `max-age`;因需 Bearer 宜 `private`)与 `ETag`(CARD-CACHE-001/002),
   `Last-Modified` 可选(CARD-CACHE-003)。未知扩展 URI 的 `A2A-Extensions` 头应被接受(JSONRPC-SVC-002、
   HTTP_JSON-SVC-002)。
10. **流式**:SSE 的 Content-Type 为 `text/event-stream`;JSON-RPC 的每个 SSE 事件都是完整的 JSON-RPC 响应,
    `result` 为 StreamResponse;SubscribeToTask 的首个事件是 Task(STREAM-SUB-001,与 `Watch` 快照先行一致)。
11. **JSON-RPC params 的字段名**:TCK 的 JSON-RPC 客户端按 proto 字段名(snake_case)发 params(`history_length`、
    `context_id`)。proto3 JSON 映射要求解析方两种名字都认;a2a-go v2.6.0 以 encoding/json 按 `historyLength` 解码
    (`a2a/core.go:830`、`a2asrv/jsonrpc.go`),snake_case 的键被忽略:GetTask 的 historyLength 在 JSON-RPC 上不生效
    (CORE-HIST-001/002,0029 §4.3),REST(查询参数)正常。上游问题;module/a2a 是否在预检里把 params 键规范化,待定。

## 5. 与设计偏离的对应

- **`A2A-Version` 缺省**(§2"其他定调"、§11.4):anet 把缺省或空的头按 1.0 处理,规范要求按 0.3。VER-SERVER-003
  只检查"返回了 result 或 error",所以会通过;记录时标为"有意偏离,通过不代表按 0.3 处理"(`summary.md` 自动附注)。
  VER-SERVER-002(显式 99.0)仍应通过。TCK 的所有客户端都显式发 1.0,其余用例不受此偏离影响。
- **TCK 钉在 A2A v1.0.0**(`263b9cf` 的 `specification/version.json`:`v1.0.0`;`tck/requirements/base.py` 的
  `TASK_NOT_CANCELABLE_ERROR` 409、`CONTENT_TYPE_NOT_SUPPORTED_ERROR` 415)。A2A v1.0.1(2026-05-26,#1627)§5.4 把
  这两个错误的 HTTP 状态都改为 400(`docs/specification.md:1183,1186`),a2a-go v2.6.0 与 anet 都按 v1.0.1。因此
  CORE-CANCEL-002(http_json,对终态任务 REST CancelTask 得 400)与 HTTP_JSON-STATUS-001(`test_content_type_not_supported_returns_415`,
  `99bed37` 起得 400)预期失败,归"有意偏离"一栏(按现行规范),不是接口问题,也不是 a2a-go 缺陷(`docs/a2a/issue-a2a-go.md`
  A11 已撤回);上游已有 a2a-tck #231、#240。JSON-RPC 一侧(`-32002`、`-32005`)不受影响。下表 2026-09-28 以前的行
  仍把 CORE-CANCEL-002 记为 a2a-go 的问题,保留原样。
- **不支持项**(§11.5):推送、GetExtendedAgentCard、gRPC 见 §3.1;它们的"拒绝形态"用例见 §4 第 4 条。
- **Message 回复**:见 §3.1 `message-response`。

## 6. 结果记录格式(不作门禁)

每次运行一个新的结果目录(非空目录拒绝写入):

| 文件 | 内容 |
|---|---|
| `run.json` | 机读摘要:`date`、`label`、`anet_commit`(脚本所在仓库)、`tck_commit`(带 `+dirty` 标记)、`sut`、`transport`、`level`、`scope`、`jsonrpc_slash_fix`、`pytest_exit`、兼容率、各状态计数、`per_transport`、各跳过分组的用例数、`failed_requirements` |
