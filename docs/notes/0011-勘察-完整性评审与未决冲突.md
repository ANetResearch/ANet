## 1. 结论摘要

1. **INV-1/INV-2(组织数据保密)的检查只覆盖注册与 profile 两个出口。** 评价上传、任务板、中继都不经过 `screenPublication`;`org.info` 的交付物含组织 id,当前经明文中继到达 hub,并可经评价上传公开(§2.1)。十份报告都没有涉及 INV-1/INV-2。
2. **daemon 本地控制台是一份独立的页面,不是 hub 的 SPA。** 两份文件字节不同(116,310 B 与 339,896 B)。04 依据过时注释认为二者相同。控制台在持有控制令牌的源里渲染 hub 返回的评价 `goal`/`deliverable`,并显示"✓ 内容已验证"(§2.2)。
3. **hub 运营面对官方 agent 主机持有 SSH 运维通道**:可启停、执行 update 命令、读取任务历史。官方 agent 是能看到解密内容的一端,所以"hub 看不到内容"对发往官方 agent 的流量不成立,除非拆开运维通道(§2.3)。
4. **现有的官方 agent 与控制面下游消费者没有被盘点**:ai-studio(bmax,以 root 运行,自带按 AID 的允许名单,`datasets.harvest: true`)、Research-Galaxy agent-runtime、ANetOS-Web hubkeeper。它们直接调用控制 API(`/threads`、`/message`、`/end`、`/end-accept`、`/accept`),05/08/02 提议的控制面与任务语义改动会让它们失效(§2.4)。
5. **Hermes 上游自带 A2A v1.0 插件**,既是客户端也是服务端。08 只按 MCP 接入 Hermes;02 §13.1 假定本机 agent 通常不是 A2A 服务端,对 Hermes 不成立(§2.5)。
6. **联邦转发会把完整信封(当前为明文载荷)依次发给每个对端 hub,直到有一个接收。** 起始 hub 不落盘;04 "两个 hub 各存一份"的说法不准确(§2.6)。
7. **安装脚本与二进制由 hub 主机提供。** "hub 不可信"的威胁模型要求发布签名先于 E2E 落地;同一源下还运行着处理用户内容的 `/os` 演示(§2.7)。
8. **`anet pull` 用对端给的文件名覆盖目标目录中的同名文件**(§2.8)。
9. **滚动升级没有 daemon↔daemon 的版本信号**:旧 daemon 对无法解码的载荷 ack 后丢弃,不报告。hub 的 `X-ANet-Wire` 只约束 daemon↔hub(§2.9)。
10. **报告之间有 5 处设计冲突需要产品决定**:发送方对 hub 是否可见(03 对 04);入站默认值用 `approve` 还是 `false`(05 对 08);只作请求方的节点不发卡片,那么加密公钥发布在哪里(07 对 03);interaction id 在中继中隐藏,却在评价与结算中公开(03/04 对 04/06);本地 A2A 令牌是否与控制台共用(05 对 07/08)。另有 4 处事实性不一致,已核对(§3)。

### 2.1 INV-1 / INV-2 只守注册与 profile,评价上传、任务板、中继不经检查

  - `modules.go:80-86` 的注释把"hub 中继按设计承载 CogUnit"作为不在 p2p 路径上加 INV-1 检查的理由。该理由以"hub 是可信传输层"为前提。
- **行为**:
  1. 组织 id 与成员凭证经明文中继到达 hub,可被 hub 解码(harvester 即在解码中继载荷,见 04 §2.7)。
  2. 请求方对一次 `org.info` 交互执行 `anet review` 后,交付物(含组织 id)随评价上传,在 `GET /agents/{aid}` 与 `GET /fed/v1/reviews` 上公开(04 §2.3、§2.4)。

- **发现方式**:从 `screenPublication` 的调用点反查所有向 hub 发出数据的路径(`grep hubPost|http.NewRequest`),再追踪 `org.info` 的结果如何进入交付物。
- **对设计的要求 [推断]**:
  - E2E 落地后,`modules.go:80-86` 的理由需要改写。
  - 评价、任务板、以及今后任何"对外可读"的出口都要纳入同一个检查点。
  - 检查应作用于解码后的字段值,不作用于 base64 字节。

### 2.7 发布源与 hub 同机;同源还运行着处理用户内容的服务

- **位置**:

### 2.15 A2A 引入、而各报告均未设计的输入面

以下均为 **[推断]**,依据是 A2A 规范与 01 已核实的 a2a-go 行为:

1. **推送通知**:a2a-go 默认的 HTTP 推送发送器拒绝回环与私有地址(01 §3.2)。本机 A2A 客户端通常在 127.0.0.1 上接收 webhook,默认发送器无法推送给它们;若放开回环,又会成为对本机服务的 SSRF 入口。需要明确是只支持轮询与 SSE,还是对推送目标做允许名单。
2. **`FilePart.url`**:本机客户端可能以 URL 形式提交文件。由 daemon 去取,会产生 SSRF 或读本机文件的问题(01 §4.3 C6 已指出卡片解析器接受 `file://`);把 URL 原样转发给远端,则把本机可达的地址泄露给对端。需要规定 daemon 对 `url` 形式的 Part 如何处理。
3. **本机多客户端隔离**:08 §8.3 只设计了一个 `a2a_token`。a2a-go 的任务隔离依赖 `CallContext.User`(01 §3.4)。所有本机客户端共用一个令牌时,Claude Code、Hermes 等可以互相 `ListTasks`/`GetTask`。是否按客户端签发令牌需要决定。

## 4. 对后续设计阶段的输入(按依赖顺序)[推断]

1. 在 C2 v2 定稿前,先决定 X1(发送方可见性)、X3(请求方节点的密钥发布)、X4(interaction id 的公开范围)。

6. 在 08 的接入方案中加入 A2A 客户端接入(至少 Hermes 的 `a2a_agents`)与令牌分发;在 02 的提供侧映射中加入"daemon 作为 A2A 客户端转交给本机 A2A 服务端"一条(§2.5)。
7. 联邦转发改为按签名卡片中的 home hub 定向发送(§2.6)。
8. 修复 `Pull` 的覆盖问题(§2.8),并对 A2A `FilePart` 的落盘采用同一规则。
9. 规定 daemon↔daemon 的能力或版本信号与明确拒绝,并在 prodtest 中加入混合版本段(§2.9)。
10. 为 ANetCore 做一次显式的依赖决定(a2a-go 是否进入 ANetCore),并把黄金向量的换代作为一个整体计划(§2.12)。

12. 对外文档按 §2.13 的表逐条改写;E2E 落地前不得出现"hub 看不到内容"的表述。
