## 2. 环境与做法

`scripts/interop/up.sh`(本轮新增,按 `joint-a2a.sh` 的做法)在一个端口块上起 hub 与三个 daemon,留着给各客户端用:

| 端口 | 用途 |
|---|---|
| 47400 | hub(空数据目录起;注册即得 100 额度,soak 前停 hub 用 `anet-hub -grant` 加额度) |
| 47401 / 47403 | requester 控制面 / **本机 A2A 接口**(`a2a_addr.txt` 预写钉住) |
| 47402 / 47404 | provider 控制面 / 本机 A2A 接口 |
| 47405 | provider 的能力后端(`a2aprobe backend`,带服务令牌) |
| 47406 | 项 3 的 Python SDK 服务端(TCP 形态) |
| 47407 / 47408 | 第二个请求方 other(Q23 与非信任对端要两个对端) |

- requester 与 other:`auto_max 0`、`agent_max 10`、`agent_daily_max 1000`,provider 在 `payees.allow`。
- provider:`closed`,requester 与 other 在 `peers.allow`;三个公开能力 `interop.digest.free`(免费)、
  `interop.digest.paid`(1,agent 档内)、`interop.digest.pricey`(15,超 agent 档),同一个后端算 SHA-256;
  文本任务由 `a2aprobe responder` 答 "echo: <正文>"(含 `[hold]` 的不答),或经 `up.sh backend` 改由 §11.6 后端答。
- 客户端脚本都在 `scripts/interop/`,每项检查输出一行 `PASS/FAIL/NOTE id: 说明`,读 `up.sh` 写的 `env.json`。

## 3. 项 1:官方 Python SDK(`a2a-sdk` 1.1.5)

`scripts/interop/py_client.py`。只用 SDK 文档里的公开面:`A2ACardResolver`、`ClientFactory` + `ClientConfig`
(`supported_protocol_bindings` 分别为 JSONRPC 与 HTTP+JSON)、`AuthInterceptor` + `CredentialService`(按卡片的
Bearer scheme 带令牌)、`ClientCallContext.service_parameters` + `with_a2a_extensions`(激活 a2a-x402)、
`a2a.utils.signing.create_signature_verifier`。

### 3.1 卡片与签名

- 不带令牌取卡片:`AgentCardResolutionError`(401);带令牌:代理卡片,接口 `JSONRPC`、`HTTP+JSON`;基址别名
  `GET /a2a/v1/agents/<aid>` 返回同一张卡。
- 签名:`create_signature_verifier(key_provider, ["EdDSA"])`,key provider 按 `kid`(`did:anet:<AID>#<seq>`)从 hub 的
  `/agents/<AID>/jwks.json` 取钥(卡片有 `jku` 时用 `jku`,并核对它是本 hub 的地址)。**代理卡片**(本机 daemon
  签,无 jku)与**网络卡片**(hub 注册表原字节,provider 签)都验过;改过名字的代理卡片验不过;代理卡片
  `anet-origin` 的 `originCard` 解码后与 hub 的字节相同;`ClientFactory.create_from_url(signature_verifier=…)` 通过。
  anet 的 §8.4.1 规范化与 a2a-python 一致(0012、Q7 的结论在真 SDK 上成立)。

### 3.2 任务操作(两种绑定各一遍)

阻塞 SendMessage(contextId 保留、`anet.reply` 为 "echo: …"、`anet.receipt_verified=verified`)、returnImmediately
再 GetTask、SendStreamingMessage(事件 task → status_update → artifact_update → status_update)、
GetTask(historyLength=1)、ListTasks(contextId,新在前,totalSize;pageSize=1 翻页)、CancelTask(provider 侧也转
canceled;再取消得 `TaskNotCancelableError`)、SubscribeToTask(进行中的任务,订阅期间 provider 作答 → completed;
已终止的任务被拒)、TaskNotFound、推送配置得 `PushNotificationNotSupportedError`、错误令牌 401;能力调用两种写法
(`metadata["anet.skill"]` + DataPart 参数、DataPart `{skill,args}`)得 `anet.result` 与 `anet.effect_status=OK`;
非 ASCII 文本(中文、emoji、希伯来文、U+202E)逐字回显;3 MiB 文本经流式回显完整;raw 文件 part 收为附件;
url part 得 `InvalidParamsError`;ListTasks 的 `status`、`historyLength=0`、`statusTimestampAfter`、`includeArtifacts`。

**与 anet 投影一致**:对阻塞文本任务、能力任务、付费任务各取一次,SDK 解析出的 Task(`MessageToDict`)与同一任务的
JSON-RPC GetTask 原始字节逐字段比较,再与控制面 `/tasks/get` 比较状态与 `anet.*`/`x402.*` 元数据:一致。只有两处
表示差异,不是语义差异:SDK 把 Struct 里的整数读成浮点(`anet.state_seq: 2.0`);时间戳 anet 写
`…36.44Z`、protobuf 写 `…36.440Z`(RFC 3339 都合法)。

### 3.3 付款(a2a-x402)

激活扩展后:付费能力 → `input-required` + `payment-required`,响应回显 `A2A-Extensions`;同一任务上
`payment-submitted` + `anet.payment.accept`(把 SDK 读到的选项原样送回)→ completed、`payment-completed`、
一张成功收据、交付物带 sha256;超 agent 档 → `input-required`、`anet.reason=needs_operator_approval`;
`payment-rejected` → canceled;付款消息走 SendStreamingMessage 同样完成;不激活扩展时 → `anet.reason=
payment_extension_not_activated`。SDK 把选项里的 `maxTimeoutSeconds: 300` 发成 `300.0`,daemon 仍认作同一选项
(a2a-go 解码成 float64 再编码,§8.7 的比较不受影响)。

**P1(SDK)**:JSON-RPC 的 SubscribeToTask 对已终止任务,anet 按 §11.4(Q31)以 400 + JSON-RPC error 对象回答;
SDK 的 JSON-RPC 流式读取只在 200 时读错误体,非 200 只报 `A2AClientError: HTTP Error 400`,错误名丢失(HTTP+JSON
绑定读得出 `UnsupportedOperationError`)。三个 SDK 对"流开不起来"的三种答法各读各的,没有一种三者都读对且不被
a2a-tck 判为"开了流"(对照表见 `issue-a2a-python.md` P1、`issue-a2a-go.md` A12)。anet 保持现状。

另:SDK 的 `get_extended_agent_card` 在卡片未声明 `extendedAgentCard` 时直接返回手里的卡、不发请求;服务端本身
对 GetExtendedAgentCard 回 `-32004`(直接发 JSON-RPC 核对)。

## 4. 项 2:官方 JS SDK(`@a2a-js/sdk` 1.2.1)

`scripts/interop/js_client.mjs`,检查项与 §3 相同(`DefaultAgentCardResolver`、`ClientFactory` +
`JsonRpcTransportFactory`/`RestTransportFactory`、`createAuthenticatingFetchWithRetry` 带 Bearer、
`serviceParameters` + `withA2AExtensions`、`verifyAgentCardSignature`)。76 项全过;JS SDK 读得出 anet 非 200 的
JSON-RPC 流式错误(`JsonRpcUnsupportedOperationError`)。三处差异,都在 SDK 一侧:

- **J2 卡片路径**:`resolve(baseUrl)` 按 URL 引用规则拼 `.well-known/agent-card.json`,不以 `/` 结尾的基址会丢掉最后
  一段(AID),取到 `/a2a/v1/agents/.well-known/agent-card.json` → 404。基址写成 `…/<aid>/` 即可。a2a-python 与
  Hermes 是拼接(先去掉末尾 `/`),a2a-go 对带路径的 URL 不追加。规范只写了域名根下的 well-known,带路径前缀的
  agent 怎么拼没说。GUIDE §6.8 已写明 JS 的写法。是否把 `GET /a2a/v1/agents` 条目的 `url` 改为以 `/` 结尾(并加
  带 `/` 的卡片别名路由,a2a-go 才能用)留给产品负责人(§10)。
- **J1 验签(SDK 缺陷,安全相关)**:`canonicalizeAgentCard` 对 SDK 自己解析后的卡片做 `AgentCard.fromJSON`,
  oneof 成员(`securitySchemes.*.httpAuthSecurityScheme`)在这一步丢失,整个 `securitySchemes` 不进签名原像。
  结果:SDK 的解析结果、`Client.getAgentCard(…, verifier)` 都验不过 anet 的代理卡片(把卡片以 JSON 形式,
  `AgentCard.toJSON(card)`,交给 verifier 则通过;网络卡片没有 `securitySchemes`,直接通过)。反向也核对了:
  JS SDK 用自己的类型签出的卡片,a2a-python 验不过,而 JS 自己的验签在 `securitySchemes` 被整个替换后仍通过——
  签名不覆盖安全方案。草稿 `issue-a2a-js.md` J1,建议走 Security Advisory 私下报告。
- **J3**:见 §8.1。

## 5. 项 3:Python SDK 写的服务端作为 provider 的 §11.6 后端

`DefaultRequestHandler`、`InMemoryTaskStore`、`create_agent_card_routes`/`create_jsonrpc_routes`/`create_rest_routes`,

### 5.1 过程中遇到的三件事

1. **我方后端的错误,anet 处理得当**:最初的执行器在 `context.current_task is None` 时先调 `TaskUpdater.submit()`,
   SDK 1.x 要求先入队 Task 本身,每个请求都以 `Agent should enqueue Task before TaskStatusUpdateEvent event` 失败。
   anet 按 §11.6 把任务留在收件箱、记日志(`module/a2a/backend.go:378`)、不回复、不记证据。改为先入队
   `new_task(...)` 后通过。SDK 的易用性问题记为 `issue-a2a-python.md` P2。
2. **失败的转发不重试**:留在收件箱的任务在 daemon 运行期间不再交付(`internal/daemon/inbound_tasks.go`
   `feedInbound` 的 `seen` 以"历史长度:末条消息 id"记已交付,失败也记上);修好后端后这两个任务一直 submitted,
   直到 provider 重启才重新交付并完成。这符合 §11.6"任何失败都留在收件箱"的写法,但后端短暂不可用(重启、
   端口未就绪)时请求方会一直等(Hermes 的阻塞调用是 3600 s)。建议对可重试的失败(连不上、超时、5xx)按退避
   重交,见 §10。
3. **UDS 路径核对**:socket 放在 0775 的目录下被拒("writable by group 1001 … set socket_group")。组 1001 是本用户的
   私有组(Ubuntu 默认 umask 002 下目录就是 0775)。改为 0700 目录后通过。拒绝本身正确;对"只有本用户的私有组"
   是否放宽(同 `scripts/lib.sh` `own_dir` 的判断)留给 §10。

### 7.2 `claude -p`

`claude -p "列出 agent,并给 <provider AID> 发一个任务:…等待结果并报告。" --max-turns 6 --allowedTools

### 7.4 缺陷:`list_tasks` 一页可达数 MB(已修 `048997b`)

长时间运行之后(§8.2,requester 上有 3 MiB 的回显任务),MCP `list_tasks(page_size=20)` 返回 **9.4 MB** 文本
(修前 `internal/mcpserv/tools.go:233` 把控制面的页原样转出,页里每个任务的最新一条消息不设上限)。
§12 让 `list_tasks` 缺省 `history_length 1`,就是为了"免得一页任务灌入大量不可信的对端文本",但单条消息没有上限:
一条大回复在它的任务还在最近一页时,随每一页整条带出。Claude Code 对单个 MCP 工具结果有上限(`MAX_MCP_OUTPUT_TOKENS`,缺省 25000 token),
超过即报错,`list_tasks` 于是一直不可用;对端也可借此往请求方的模型上下文里灌任意长的文本。

修复:`a2ashape.TaskWithin(t, max)`(与流式事件的 `TaskForStream` 共用取舍顺序:metadata、status.message、产物、
history 从新到旧;最新一条放不下时换成注明大小的说明、标 `anet.truncated`,不静默丢弃);控制面 `/tasks/list` 加可选
`max_task_bytes`(0 不限、负数 400,A2A ListTasks 不变);MCP `list_tasks` 固定传 8192,工具描述写明。回归测试
`TestTaskListHoldsEachTaskToMaxTaskBytes`(去掉截断:单个任务 18 MB,红)、`TestTaskWithinHoldsAListedTaskToItsBound`、
`TestEachToolSendsTheRequestTheRouteExpects`(去掉 mcpserv 那一行即红)。修后(同一份数据,重新 `anet agents wire
claude`):`list_tasks(page_size=20)` 23.9 KB,最大的一个任务 3.1 KB,2 个被截;`page_size=100` 118 KB、7 个被截;
`mcp_check.py` 仍 8 / 0。

单任务读取(`send_message`、`get_task`、`wait_task` 的应答)仍返回全文:3 MiB 的回复同样会超过 Claude Code 的工具
结果上限,模型连任务 id 都拿不到。是否对 MCP 的单任务读取也设上限(并给出读全文的别的途径)留给 §10。

## 8. 长时间运行

### 8.1 挂起 7 分钟(`long_hold.py`、`js_long_hold.mjs`)

provider 不答的任务(`[hold]`)开着 420 s,再由 provider 控制面 `/tasks/reply` 作答:

| 客户端 | 形态 | 结果 |
|---|---|---|
| Python SDK | SendStreamingMessage(JSON-RPC)、SendStreamingMessage(HTTP+JSON)、阻塞 SendMessage | 三个都开 422 s 后收到答复(流式靠 anet 每 15 s 的 SSE keep-alive;阻塞调用期间线上无字节,httpx 按配置的超时等) |
| JS SDK | SendStreamingMessage | 431 s 后收到答复 |
| JS SDK | 阻塞 SendMessage | **301 s 失败**:`TypeError: fetch failed`(`UND_ERR_HEADERS_TIMEOUT`)。Node 的 fetch(undici)缺省 300 s 收不到应答头即放弃;任务本身继续,之后正常完成 |

J3 是客户端缺省值的问题:anet 的阻塞调用按 A2A §3.2.2 等到终态或中断态才回应答头。GUIDE §6.8 写明 JS 客户端对

怎样传入不设上限的 fetch。

### 8.2 两个 SDK 套件交替一小时(`soak.py`)

`py_client.py`(82 项,含 3 MiB 流式回显)与 `js_client.mjs`(76 项)交替,62 分钟 21 轮(Python 11、JS 10),
**1662 项通过、0 失败**;每轮之间采样各进程与数据目录:

| 进程 | RSS | 打开的描述符 | 线程 |
|---|---|---|---|
| requester anet | 81–151 MB | 17–19 | 13–14 |
| provider anet | 66–133 MB | 19–21 | 14 |
| other anet(空闲) | 23 MB | 16 | 10–11 |
| anet-hub | 44–67 MB | 19–21 | 13–14 |

无上升趋势,无 panic、无 ERROR 日志。requester 与 provider 的数据目录各从 140 MB 长到 1.03 GB(809 个任务;每轮两条
3 MiB 的消息占大头:一次 3 MiB 的文本往返在请求方存 goal 3 MiB、request_doc 6 MiB、result(对话记录)6 MiB、两条
消息 6 MiB,约 7 倍),hub 16 → 22 MB。`/balance` 的应答随 hub 账本条目增长到 100 条后封顶(12 KB)。

**但每轮耗时单调变长**:Python 93 → 134 → 157 → 148 → 171 → 180 → 205 → 220 → 228 → 245 → 301 s,JS 106 → 251 s。
逐项计时(`PYCLIENT_TIMES=1`)的一轮 290.8 s 里,ListTasks 的四项各 18–19 s,SubscribeToTask 的两项各 ~50 s(检查脚本
自己经 provider 控制面 `/tasks/list role=inbound` 找任务)。直接测:本机 A2A 接口的 ListTasks(pageSize 1)14.5 s,
控制面 `/tasks/list` 不带过滤 0.11 s、带 `role=outbound` 33 s、带 `peer` 13.7 s。

**根因**(修前 `internal/runtime/interactions/interactions.go:1056`(`ListPage` 的整行排序查询)、`:1106`(`Count`)、
`tasks.go:89`(`FindByClientMessage` 按 `m.metadata` 过滤);表结构 `interactions.go:306`):
interaction 行内存 `goal`、`request_doc`、`result`,长消息时各数 MB;SQLite 读一行里排在大列之后的列,要沿大列的
溢出页链一页页走过去。带 role 或 peer 过滤的列表(本机 A2A 接口的每次 ListTasks 都按 role=outbound、peer=AID
限定),SQLite 选 `idx_ix_peer`/`idx_ix_pay` 做等值、再把每个匹配行**整行**放进临时 B 树按 `state_at` 排序——每次
调用读完该对端全部任务的全部大列(复制出的库上 `EXPLAIN QUERY PLAN`:`SEARCH … USING INDEX idx_ix_peer …; USE TEMP
B-TREE FOR ORDER BY`,13.2 s)。查重同理:未给 contextId 的 SendMessage 要读该对端所有消息的 `metadata`,它排在
`body` 之后(0.15–0.3 s,随数据线性增长)。soak 采样用的 `/tasks/list` 不带过滤,走 `idx_ix_state_at` 的有序扫描,
所以采样里看不出来。

**修复 `c50e70b`**:覆盖索引 `idx_ix_list(state_at, seq, role, peer_aid, state, is_capability, trust, context_id)`;
`ListPage` 分两步(先 `INDEXED BY idx_ix_list` 取一页的 seq,再按 seq 取整行),`Count` 只读该索引,游标条件改为行值
`(state_at, seq) < (?, ?)`;context 过滤仍走 `idx_ix_context`。查重加表达式索引 `idx_msg_client`(表达式与查询共用
`clientMsgIDExpr`)。回归测试 `TestListingReadsTheCoveringIndex`(六种过滤的列表与计数的查询计划都须走覆盖索引、
无排序;旧查询红)、`TestClientMessageLookupReadsAnIndex`(旧查询红)、`TestListPageTwoStepKeepsOrderAndRows`。
升级时两个索引各建一次(1 GB 的库约 1 s)。

**测试夹具**(`a643ee4`):`a2aprobe responder` 每次轮询取全部入站任务(修前 `tools/a2aprobe/provider.go:132`,page 100、
history 20),读取上限 16 MiB(`provider.go:178`);
几个 3 MiB 任务答完之后一页就超过上限,之后每次轮询都读到截断的 JSON,不再答复任何任务(soak 之前的 JS 运行里
表现为三组操作超时)。改为按三个未终止状态各取一页、history 1;`TestResponderIsNotStoppedByLargeFinishedTasks`。

### 8.3 并发突发(`burst.py`)

同一时刻起 N 个阻塞 SendMessage(JSON-RPC)、N 个 SendStreamingMessage(HTTP+JSON)、N 个免费能力调用,都经 Python
SDK、同一个本机 A2A 接口(修复后的节点,1 GB 数据上):

| N | 文本阻塞 | 流式 | 能力调用 | 墙钟 |
|---|---|---|---|---|
| 30 | 30/30,中位 2.9 s、最长 3.8 s | 30/30,3.0 / 3.4 s | 30/30,1.8 / 1.9 s | 3.8 s |
| 100 | 100/100,5.7 / 13.9 s | 100/100,5.5 / 13.8 s | **30/100**;6 个 `rejected`(`quota_caller_per_min`),64 个到客户端超时(600 s)仍 `submitted` | 600.9 s |

文本与流式在 hub 的发送限流(`429 send rate exceeded`)下排队重投,全部按序完成。能力调用超出 provider 公开能力的
每调用方每分钟配额:provider 拒了 70 个(证据 `anet.delegation.refused_summary` `by_reason: quota_caller_per_min: 70`),
但拒绝通知按设计 X2/C15 限速(`reject_notice.per_peer_per_hour` 6),只发出 6 个,其余静默丢弃
(`daemon.log`:`notice-rate-limited (count 10)` 等)。请求方收不到任何回答,64 个任务停在 `submitted`,A2A 阻塞调用
一直等到客户端自己超时(Hermes 条目是 3600 s),MCP `wait_task` 同样。这是"拒绝的副作用有界"的取舍,不改;对请求方的
影响与建议见 §10。

## 10. 遗留

需要产品负责人或后续工作包决定的:

1. **配额拒绝的静默(§8.3)**。超出 `reject_notice` 限速后,公开能力的配额拒绝静默丢弃,请求方的任务永远 `submitted`。
   可选:请求方对能力调用设"无回答"期限(到期置 failed、`anet.reason=no_answer`);或配额拒绝(对方是本节点正在服务的
   调用方,不是陌生人)不计入拒绝通知的限速;至少在对外文档与 §21 写明。
2. **§11.6 后端失败不重试(§5.1)**。建议对可重试的失败(连不上、超时、5xx)按退避重交,不可重试的(4xx、答复无内容)
   仍留收件箱;并在 doctor/`inbound_pending` 里能看到"转发失败留在收件箱"的任务。
3. **MCP 单任务读取无上限(§7.4 末)**。`send_message`/`get_task`/`wait_task` 对一个 3 MiB 回复的任务整条返回,超过
   Claude Code 的工具结果上限,模型连任务 id 都拿不到。可考虑对 MCP 的单任务读取同样设上限(例如 64 KiB,截断处注明
   用 `anet` CLI 读全文)。
4. **JS SDK 与基址(§4 J2)**。是否让 `GET /a2a/v1/agents` 条目的 `url` 以 `/` 结尾(并为 a2a-go 加带 `/` 的卡片别名
   路由),使 `@a2a-js/sdk` 的 `createFromUrl(url)` 直接可用;目前只在 GUIDE 写明。
5. **流式调用的错误形态(§3.3 P1、A12)**。三个 SDK 没有一种共同读得对的答法;anet 保持 §11.4(Q31)的非 200。
   规范讨论时带上对照表。
6. **UDS 路径核对与用户私有组(§5.1)**。Ubuntu 缺省 umask 002 下目录为 0775、组为本用户私有组,`backendconn` 拒绝;
   是否对"成员只有本用户"的组放宽,与 `scripts/lib.sh` `own_dir` 的判断一致。
7. **存储放大(§8.2)**。一次文本往返在请求方约存 7 倍正文(goal、request_doc、result 与消息各一份),文本任务没有
   保存期;长消息多的节点数据目录增长快。
8. **Claude Code 真跑**。临时 HOME 下未登录,`claude -p` 没能真正调用模型;需要一个可登录的测试账号补跑一次,记录
   实际的工具调用序列与 token 数(本文 §7.3 是按内容量估的)。
9. **代理卡片的输入模式**。closed 的 provider 对允许名单内的请求方接受文本任务,但网络卡片只列能力,代理卡片的
   `defaultInputModes` 于是只有 `application/json`;按卡片检查输入模式的严格客户端会以为不能发文本(两个 SDK 都不检查)。
10. SDK 草稿(`issue-a2a-python.md`、`issue-a2a-js.md`)按标注待更多测试;J1 是安全相关,只走 Security Advisory。
11. **SQLite 连接池无上限(§8.4)**。hub 与 daemon 都没有 `SetMaxOpenConns`;并发突发会开出几百个连接与文件描述符
    (有界,但随并发量而定)。建议设一个上限(例如 32),让突发在池里排队。
12. **其余逐行读长列的查询**。`interactions.List`(按 role、seq 翻页,整行本就要读)、`peers.go:315` 的活动交互判断
    (淘汰 peer 身份时按对端读 `state`)与 `retention.go:69` 的每小时清理仍会读到长列之后的列;本轮没有测到它们在热路径上,
    未改。
