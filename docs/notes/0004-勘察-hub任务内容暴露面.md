# 04 · ANetHub 任务内容暴露面调查

调查对象：ANetHub `c4d08da`，交叉核对 ANet `840b8ea`、ANetCore `59086ea`。本阶段只读，未修改任何仓库文件。

标注约定：
- 未加标注的陈述均由阅读代码核实，给出 `仓库/路径:行号`。
- `[推断]` 表示由代码推出、但未运行验证的结论。

"任务内容"在本报告中指：委派目标（goal / TaskDoc intent）、会话消息正文、交付物（deliverable / transcript）、附件字节、请求文档（request_doc）。AID、时间、计数、CID 等归入"元数据"，第 7 节单列。

## 1. 结论摘要

目标不变量是"hub 只做传输，永不看到任务内容"。现状与它有七处冲突，其中四处把内容公开给未认证的 HTTP 调用方。

| # | 面 | 内容 | 存储位置 | 谁能读 | 冲突程度 |
|---|---|---|---|---|---|
| A | relay 转发 | DelegateReq（goal、附件字节）、ChatMsg（正文、附件）、ResultResp（交付物 transcript） | `hub.db` `relay_message.payload`，明文 CBOR | hub 进程、admin 进程、磁盘与备份的持有者 | hub 持有全部明文 |
| B | 评价 | goal、完整 deliverable、原始 request_doc、原始 deliverable 字节 | `review.goal/deliverable`、`review_blob.request_doc_raw/deliverable_raw` | **公网匿名**：`GET /agents/{aid}` | 内容公开且永久保留 |
| C | 联邦评价同步 | 原始 request_doc、原始 deliverable（base64） | 发送侧读 `review_blob`；接收侧不落盘内容 | **公网匿名**：`GET /fed/v1/reviews`（开启 discovery 时） | 内容公开 |
| D | 访客模式 | 访客消息、附件、agent 回复、交付 transcript | `relay_message`（短期）+ hub 内存；hub 持有代签私钥 | hub 进程；浏览器经 hub 中转 | hub 是明文代理且是签名主体 |
| E | taskboard | 卡片 title、submit/reject/block 的 note | `taskboard.db` `cards`、`card_events` | **公网匿名**：`GET /tasks/board`、`GET /tasks/cards/{id}` | 内容公开 |
| F | admin 采集 | 从 relay 解码出的 goal、正文、交付物（每条截 16 KiB） | `admin/datasets/hub-relay/**.jsonl`、`admin.db session.goal` | admin token 持有者；文件 0644 | 永久副本，超出 relay 保留期 |
| G | admin 评价视图 | review 的 goal、deliverable（截 2 KiB） | 读 `hub.db` | admin token 持有者 | 运营者可读内容 |

另有两项直接相关的现状：
- relay 只有 poll/ack 有认证，`/relay/send` 无认证、`from_aid` 不校验、无速率限制，应用层单请求上限 1 GiB（第 3 节）。
- 对外表述与实现不一致：首页写"访客模式……数据不留存"（`ANetHub/webui/src/components/Hero.tsx:80-81`），而 admin 采集器按 rowid 读取 relay 行，含访客行（第 2.7 节）；`docs/DATA-ASSETS.md:1-5` 把 relay 流量定位为训练数据资产。

## 2. 逐面详述

### 2.1 relay 存储与转发（面 A）

**内容是什么。**
- 三种 kind：`delegate`、`result`、`message`（`ANetHub/internal/aghub/aghub.go:125-130`）。
- `delegate` 的 payload 是 `delegation.DelegateReq` 的 CBOR 编码：签名 TaskDoc 字节、KEL、interaction_id、内联附件字节（`Data`），以及可选的 x402 `Payment`（`ANetCore/delegation/delegation.go:37-55`、`:62-68`）。
- daemon 构造 TaskDoc 时只放入 `Intent{Summary: goal, Body: goal}`（`ANet/internal/daemon/daemon.go:281-291`），序列化后直接作为 relay payload 发送（`ANet/internal/daemon/relay.go:185-190`，经 `ANet/internal/daemon/transport.go:40-46` POST `/relay/send`）。
- `message` 的 payload 是 `ChatMsg`（正文 `Body`、附件、推理流字段）。该类型不签名，注释写明"the Hub is trusted as the relay"（`ANetCore/delegation/delegation.go:129-133`）。
- `result` 的 payload 是 `ResultResp{Deliverable, Receipt, KEL}`（`ANetCore/delegation/delegation.go:84-102`）。其中 Deliverable 是 transcript JSON `[{from, body, attachments}]`（`ANet/internal/daemon/delegation.go:336-368`）。

**是否加密。** 否。
- payload 是上述结构的明文 CBOR。hub 侧注释称其 "opaque"（`ANetHub/internal/aghub/aghub.go:121`、`:906-907`），但 admin 采集器（2.7）和访客代理（2.5）都在直接解码它。
- ANetCore 已有匿名 sealed box 原语 `identity.SealTo` / `Open`（`ANetCore/identity/encrypt.go:71-73`、`:90`），但在 ANet、ANetCore、ANetHub、ANetLink 的非测试代码中没有调用点（`grep SealTo` 仅命中定义与 `encrypt_test.go`）。

**存储位置。**
- `relay_message(id, to_aid, from_aid, kind, interaction_id, payload BLOB, created_at, delivered_at)`（`ANetHub/internal/aghub/aghub.go:392-402`）。
- 写入在 `RelayEnqueue`（`aghub.go:908-930`），读取在 `RelayPoll`（`aghub.go:982-1011`）。
- ack 只写 `delivered_at`，不删除该行（`aghub.go:1015-1035`）。
- 应用代码中删除 relay 行的只有两处，都限于访客 broker 的 AID（`aghub.go:1041-1055`、`:1063-1077`）。

**保留期。** 由部署脚本 `ANetHub/deploy/hub-db-roll.sh` 决定，不在二进制里：
- 已投递行保留 7 天，未投递行保留 14 天（`hub-db-roll.sh:4-5`、`:20-38`）。
- 每周日 `VACUUM INTO` 生成整库备份，保留最近两份（`hub-db-roll.sh:43-54`）。备份包含 `relay_message`、`review`、`review_blob` 全表。
- `[推断]` 删除后未设置 `PRAGMA secure_delete`，被删页在下次 `VACUUM` 之前仍留在数据库文件的空闲页里。

**谁能读。**
- 公共 HTTP 只把邮箱内容返回给持有该 AID 私钥的调用方（`ANetHub/internal/aghub/server.go:954-983`）。
- admin 进程以同一 `hub.db` 文件为只读源，`RelayRowsSince` 读取全部 payload（`ANetHub/internal/admin/hubread.go:299-327`）。
- 磁盘与备份的持有者可读全部内容。

**deregister。** 注销保留邮箱中未投递的消息，只报告数量（`ANetHub/internal/aghub/deregister.go:48-65`）。这些内容随后按 14 天规则清除。

**联邦转发。**
- 本地未知收件人时，经 `SetForwarder` 把 payload 原样交给联邦（`ANetHub/internal/aghub/server.go:899-911`）。
- `Envelope` 携带 `from_aid / kind / interaction_id` 与 base64 payload（`ANetHub/internal/federation/federation.go:107-124`）。
- 对端 hub 验签后把 payload 写入自己的 `relay_message`（`federation.go:331-334`、`:366`）。明文因此在两个 hub 各存一份。

**需要的改动。** 见 4.2：payload 端到端加密，`from_aid / kind / interaction_id` 移入密文，ack 即删，备份排除 relay 表。

### 2.2 `completed_task` 统计

- 表结构为 `(interaction_id, provider_aid, requester_aid, completed_at)`（`ANetHub/internal/aghub/aghub.go:403-411`）。
- `RelayEnqueue` 看到 `kind == "result"` 时写入一行，`provider_aid` 取自发送方声明的 `from_aid`（`aghub.go:921-928`）。
- 该表不含内容。它依赖 hub 能读懂 `kind`，并依赖未经认证的 `from_aid`：`hRelaySend` 把 `req.FromAID` 原样传入（`server.go:918`），而 `/relay/send` 无认证（第 3 节）。
- `[推断]` 任何调用方都能用 `kind=result` 和任意 `from_aid`、`interaction_id` 提高 `/stats` 的 `tasks_completed`（`aghub.go:963`），以及 admin 的 `tasks_as_provider`（`hubread.go:83-84`）。
- 读者：`/stats` 公开计数（`server.go:332-356`）；admin 可见逐条列表（`hubread.go:178-199`，路由 `admin/server.go:128`）。

**需要的改动。** kind 进入密文后，这个派生无法再做。改为基于公开 receipt 的计数（4.7）。

### 2.3 评价与 `review_blob`（面 B）

**上传路径。**
- 需求方执行 `anet review` 时，daemon 签名评价后自动上传到 hub（`ANet/internal/daemon/control_api.go:918-945`）。上传体包含 `receipt`、`review`、`request_doc`、`deliverable`（`ANet/internal/daemon/hub_client.go:111-134`）。
- hub 把 `request_doc` 与 `deliverable` 设为必填（`ANetHub/internal/aghub/server.go:613-622`、`:630-633`）。

**hub 做了什么。**
- 调用 `evidence.VerifyInterlock(rc, rv, requestDoc, deliverable, …)`，要求内容哈希等于 receipt 中的 CID（`server.go:722`）。
- 从 TaskDoc 取出 goal，把 deliverable 转为字符串（`server.go:725-731`、`:737-746`）。
- 写入 `review.goal`、`review.deliverable`（`aghub.go:196-210`、`:727-739`），并把四份原始字节写入 `review_blob`（`server.go:665`；表结构 `aghub.go:290-296`；写入 `ANetHub/internal/aghub/reputation.go:163-169`）。

**谁能读。**
- `GET /agents/{aid}` 无认证，返回该 agent 的全部评价，含 `goal` 与完整 `deliverable`（`server.go:1047-1069`；查询 `aghub.go:884-901`；类型 `aghub.go:89-102`）。CORS 为 `*`（`server.go:1085-1096`）。
- agent 注销后，评价仍以 departed 视图返回（`aghub.go:863-880`）。代码中没有删除评价内容的路径。
- 数据模型把"verified content"作为评价的一部分对外展示（`aghub.go:85-88` 注释），`llms.txt` 也把 transcript 与评价绑定（`ANetHub/internal/aghub/web/llms.txt:136-137`）。

**同意问题。** 交付物由提供方产生，却由需求方单方面上传公开。提供方没有同意或撤回的入口（上传只校验 reviewer 已在本 hub 注册，`server.go:694-699`）。

**CID 本身的信息泄露（与"只留 CID"方案直接相关）。**
- `RequestCID = anetcid.Sum(doc)`，其中 `doc = coredet.Marshal(TaskDoc{Version:1, Tasks:[{Intent:{Summary:goal, Body:goal}}]})`（`ANet/internal/daemon/relay.go:158-162`、`ANet/internal/daemon/daemon.go:281-291`）。签名信封 `Envelope` 用 `cbor:"-"` 排除在字节之外（`ANetCore/tsir/taskdoc.go:101-104`）。**RequestCID 因此只由 goal 文本决定，不含随机数。**
- `ResultCID` 是 transcript JSON 的哈希（`ANetCore/evidence/interlock.go:87-94`），transcript 只含 `from/body/attachments`（`ANet/internal/daemon/delegation.go:336-368`），同样没有随机数。
- `[推断]` 后果有两个。其一，对低熵内容（短指令、常见问题），任何人拿候选文本算 CID，与公开的 `request_cid` 比对，就能确认内容。其二，不同需求方提交相同 goal 会得到相同 RequestCID，可被关联。
- 所以仅仅删掉 goal/deliverable 字段、保留现有 CID，不足以做到"hub 与公众看不到内容"。需要加盐承诺（4.3）。

### 2.4 联邦：评价同步与投递（面 C）

- `GET /fed/v1/reviews?cursor=` 无认证。注释说明"Unauthenticated for the same reason as the card stream"（`ANetHub/internal/federation/federation.go:523-545`）。仅在 discovery 开启时应答（`federation.go:530-533`、`:489-492`）。
- 数据来自 `Store.ReviewsSince`：选出本 hub 用户作为 reviewer、subject 已选择联邦可见的评价（`ANetHub/internal/aghub/reputation.go:67-134`），再从 `review_blob` 读出 `RequestDoc`、`Deliverable` 原始字节，base64 后放进 `FedReview`（`reputation.go:49-57`、`:124-131`、`:142-160`；JSON 适配 `ANetHub/internal/aghub/card.go:657-671`）。
- 该端点把请求文档和交付物原文公开给任何能访问该 hub 的调用方，而不仅是对等 hub。
- 接收侧 `AdmitFedReview` 解码两份内容，用于 `VerifyInterlock`（`reputation.go:187-194`、`:229`），但只把 rating、comment、receipt_cid 等写入 `fed_review`，不落盘内容（`reputation.go:247-252`；表 `aghub.go:299-310`）。所以对端 hub 不持久化内容，但每轮同步都在内存中处理明文。
- `/fed/v1/*` 直接挂在根 mux 上（`ANetHub/cmd/anet-hub/wire_federation.go:28`），不经过 `srv0.Handler()` 的 `cors / wireContract / limitBody` 包装（`ANetHub/internal/aghub/server.go:271`；根 mux 见 `ANetHub/cmd/anet-hub/main.go:250-252`）。`hForward` 自带 100 MiB 上限（`federation.go:277`）。
- 投递转发的明文问题见 2.1 末段。

**需要的改动。** `FedReview` 去掉 `RequestDoc / Deliverable`，验证改为无内容版本（4.3）。

### 2.5 访客模式（面 D）

**机制。**
- 浏览器没有身份，hub 用一个持久化的 broker 身份代为签名。私钥写入数据目录下的 `guest_identity.kel`，权限 0600（`ANetHub/internal/aghub/guest.go:216-237`）。broker 以不可见方式注册（`guest.go:183-187`）。
- 首条访客消息被 hub 包装为 broker 签名的 TaskDoc + DelegateReq（`guest.go:341-351`、`:592-603`），后续消息为未签名的 ChatMsg（`guest.go:605-610`），都以明文写入 `relay_message`（`guest.go:356`）。
- hub 轮询 broker 邮箱，解码 ChatMsg 与 ResultResp。它会把 transcript 中 provider 的正文逐条取出（`guest.go:548-588`），暂存在内存 session 的 `pending` 中，再返回浏览器（`guest.go:370-401`、`:509-545`）。附件字节在 20 MiB 以内时 base64 内联返回（`guest.go:74`、`:125-139`）。
- 路由在内核中无条件注册（`server.go:248-253`），启动时无条件启用（`ANetHub/cmd/anet-hub/main.go:241-245`），没有 build tag。

**默认接待。**
- agent 表 `guest_quota` 默认 5（`aghub.go:192`、`:425`）。
- 注册请求省略该字段时同样取 5（`server.go:542-550`）。daemon 端默认也是 5（`ANet/internal/daemon/config.go:89`、`:98-106`，经 `ANet/internal/daemon/hub_client.go:66` 发送）。
- 访客可以被路由到任何 listed 且 quota>0 的 agent，包括随机选择（`guest.go:465-486`、`:491-505`）。
- 这与既定原则 (3)"新装默认不接受任何人的委派"冲突：新装的 agent 默认对匿名访客开放 5 条消息。

**"不留存"的实际范围。**
- 已投递的访客行在每次访客 poll 时删除（`guest.go:396`），另由后台 janitor 每 5 分钟清理，并删除 30 分钟前的未投递行（`guest.go:43-45`、`:199-214`）。
- admin 采集器默认每 30 分钟按 rowid 读取所有新 relay 行（`ANetHub/cmd/anet-hub-admin/main.go:46`；`ANetHub/internal/admin/harvest.go:199-243`），不区分访客行。
- `[推断]` 一行访客消息在被清理前若恰好被采集，就会以解码后的明文进入 admin datasets 并永久保留。发往离线 handler 的访客消息最多存活约 35 分钟，与 30 分钟的采集周期重叠。首页"数据不留存"的表述（`Hero.tsx:80-81`）没有覆盖这条路径。
- 接收方 daemon 按常规流程保存访客消息，这部分属于通信对端，不是 hub。

**结构性问题。** 访客模式要求 hub 能读写明文、并以自己的密钥代签。"hub 看不到内容"与"hub 代浏览器收发"在当前设计下不能同时成立。选项见 4.4。

### 2.6 taskboard（面 E）

- 包注释声明"The board never stores task semantics, only workflow position"（`ANetHub/internal/taskboard/taskboard.go:1-5`）。实际表结构包含 `title TEXT NOT NULL` 与 `note`（`taskboard.go:52-65`、`:95-107`）。title 由调用方提供，daemon 模块把 `args.title` 原样提交（`ANet/module/taskboard/taskboard.go:259-271`）。
- note 在 submit、reject、block 时写入卡片，也写入事件表的 `detail`（`taskboard.go:193-205`、`:221-235`、`:238-250`、`:269-290`）。reject 与 block 强制要求 note（`taskboard.go:222-224`、`:239-241`）。这些字段通常是对交付物的评语或阻塞原因，属于任务内容。
- 读取无认证："Reads are open (D44: guests read)"（`ANetHub/internal/taskboard/http.go:17-19`）。`GET /tasks/board` 返回全部卡片（`http.go:82-102`），`GET /tasks/cards/{id}` 返回卡片与全部事件（`http.go:104-111`），CORS 为 `*`（`http.go:133-146`）。整个 hub 只有一块板，没有按组织或成员划分。
- `taskdoc_cid` 与 2.3 的 RequestCID 同样未加盐，可被字典确认 `[推断]`。
- 挂载在根 mux（`ANetHub/cmd/anet-hub/wire_taskboard.go:15`），不经过 `limitBody`。变更请求直接 `json.NewDecoder(r.Body)`，没有大小上限（`http.go:65`），实际上限来自 nginx。
- 可插拔：`//go:build !no_taskboard`（`wire_taskboard.go:1`），CI 矩阵已包含 `no_taskboard`（`ANetHub/.github/workflows/ci.yml:28`）。
- web UI 公开展示 title 与 cid（`ANetHub/webui/src/components/TasksSection.tsx:95-108`）。

### 2.7 admin 面（面 F、G）

admin 是独立二进制 `anet-hub-admin`，监听 loopback，由 nginx 以 `/admin` 暴露到公网（`ANetHub/deploy/nginx-admin.locations:3-11`），用单一 Bearer token 认证（`ANetHub/internal/admin/server.go:20-28`、`:104-135`）。它直接打开公共 hub 的 `hub.db`（`ANetHub/internal/admin/hubread.go:14-42`）。

**(1) relay 采集器（hub-relay 源）。** 这是 hub 侧最大的内容副本。
- `RelayRowsSince` 按 rowid 读取全部 payload，注释称其为"the ONLY payload-reading query in the admin plane"（`hubread.go:299-327`）。
- `decodeRelay` 解码三类 payload：delegate 取 TaskDoc goal，message 取正文，result 取交付物（UTF-8 时为全文），每项截断到 16 KiB；附件只保留 name/mime/size/cid（`ANetHub/internal/admin/harvest.go:97-121`、`:123-127`、`:152-196`）。
- 结果以 JSONL 追加写入 `datasets/hub-relay/sessions/<yyyymm>/…`，目录 0755、文件 0644（`harvest.go:271-305`）。首个 goal 写入 `admin.db` 的 `session.goal`（`harvest.go:319-321`；表 `ANetHub/internal/admin/store.go:112-128`）。
- 默认每 30 分钟运行一次（`ANetHub/cmd/anet-hub-admin/main.go:46`、`:143`；`ANetHub/internal/admin/server.go:803-825`），也可以手动触发（`POST /admin/api/harvest`，`server.go:126`、`:746-753`）。
- admin 包内没有任何 `os.Remove` / `RemoveAll` 调用（`grep`）。datasets 没有保留期，超出 relay 的 7/14 天保留期而永久存在。
- 读取入口：`GET /admin/api/sessions`、`GET /admin/api/sessions/{source}/{id}` 返回会话卡与前 500 条原始事件（`server.go:124-125`、`:723-744`；`harvest.go:620-652`）。admin SPA 把事件 JSON 直接渲染出来（`ANetHub/internal/admin/web/admin.html:929-948`），会话列表显示 goal 列（`admin.html:908`、`:960`）。`GET /admin/api/agents/{aid}` 同样附带该 agent 的会话（`server.go:461`、`:467-469`）。
- 设计意图写在 `ANetHub/docs/DATA-ASSETS.md:1-5`、`:25-26`：把平台流量沉淀为"可训练的 agent 交互数据"，事件字段含 `goal|body|status|deliverable`。

**(2) ai-studio 源。**
- 通过 ssh 读取官方 agent 的 `history.jsonl`，或经 monitor 的 `/api/state` 拉取 `JobRec`，字段含 `Prompt`（`harvest.go:382-405`、`:411-453`、`:458-537`）。prompt 写入会话 goal 与标题（`harvest.go:589-593`、`:612`）。

补充说明：

1. **挑战签名的重放窗口为 ±5 分钟，没有 nonce 缓存**（`relayauth.go:22`；`server.go:1032-1039`）。
   - `[推断]` 窗口内截获的 poll 签名可以重复读取该邮箱。
   - `[推断]` 截获的 ack 签名可以配合任意 `ids` 使用，把该邮箱中的任意未投递消息标记为已投递，造成静默丢失。
   - 原像不含 hub 标识，所以 `[推断]` 同一 AID 在两个 hub 注册时，签名可以跨 hub 重放。TLS 降低了截获概率，但不改变这一构造。

2. **`from_aid` 不可信，而 daemon 信任它。**
   - daemon 处理 `message` 时，把 hub 给出的 `FromAID` 作为发送者写入会话（`ANet/internal/daemon/relay.go:423-424`；`ANet/internal/daemon/delegation.go:636-676`），不核对它是否等于该 interaction 的对端 AID。ChatMsg 本身也不签名（`ANetCore/delegation/delegation.go:129-133`）。
   - `[推断]` 知道收件人 AID 与 interaction_id 的第三方可以向进行中的会话注入消息或结束协商。interaction_id 在公开评价中可见（`aghub.go:89-90`）。
   - daemon 侧对付款报价已有防范，注释写明"/relay/send is unauthenticated by design"（`ANet/internal/daemon/paylink.go:292-295`）。

3. **CORS 对所有内核路由为 `*`**（`server.go:1077-1096`）。理由是"no ambient authority"。这不影响内容暴露，但意味着任意网页都能调用 `/guest/*` 与 `/relay/send`。

4. **生产环境的 nginx 配置可能与仓库不同。** `[推断]` 运维记忆中 emax 的 nginx 为 512m（未在本次核对范围内）。仓库版本为 96m。

## 4. 改造方案

### 4.1 目标不变量（建议写入 C2 契约）

`[建议]` hub 可观察的集合限定为：

1. 收件人 `to_aid`（路由必需）。
2. 发送方 AID（仅在选择"认证发送"时，用于限流与滥用处置；见 4.2 的取舍）。
3. 密文长度（建议分桶填充）与时间戳。
4. agent 自己发布的资料：卡片、KEL、profile。
5. 不含内容的证据：receipt、review 签名对象、加盐承诺、付款收据。

hub 不得持有：任何 TaskDoc 正文、ChatMsg 正文、交付物、附件字节、`kind`、`interaction_id`，以及能解密上述内容的密钥。

**验收方式（建议作为联调测试）。**
- 在 `scripts/joint.sh` 与 `scripts/prodtest.sh` 中，用一次含随机 canary 字符串（例如 32 字节十六进制）的委派加附件走完整流程：delegate → message → result → review → federation sync → taskboard。
- 然后对 hub 数据目录全部文件（`hub.db`、`-wal`、`hub-backup-*.db`、`taskboard.db`、`admin/` 下全部文件）做字节搜索，要求 canary 出现 0 次。同时对 `/agents/{aid}`、`/fed/v1/reviews`、`/tasks/board` 的响应做同样搜索。
- mutation 验证：把加密层改为直通后，该测试必须失败。
- 按 CLAUDE.md 的"两个方向都要验"：同一测试在 daemon 侧断言 canary 能被收件方解出，防止"什么都没传"也通过。

### 4.2 relay 端到端加密

**信封（C2 wire v2）** `[建议]`：

```
RelaySendV2 { v:2, to_aid, ct, [sender_auth] }
ct = Seal(recipient_enc_key, CBOR{
        from_aid, kind, interaction_id, msg_id, ts,
        body,            // 现有 DelegateReq / ResultResp / ChatMsg 字节，或 A2A JSON-RPC 消息
        sender_sig       // 发送方 Ed25519 签名，覆盖 H(to_aid ‖ kind ‖ interaction_id ‖ msg_id ‖ ts ‖ body)
     })
```

- **先签后密，签名覆盖收件人。** 防止收件人把签名消息转封给第三方冒充原发送方。解密后 daemon 必须校验 `sender_sig`，并校验 `from_aid` 等于该 interaction 的对端，从而修复第 3 节第 2 点。ChatMsg 也因此获得发送方认证。
- **加密原语。**
  - 现有 `identity.SealTo` 是匿名 sealed box：没有前向保密，并复用 Ed25519 签名密钥派生 X25519（`ANetCore/identity/encrypt.go:5-17`，注释已列出这一耦合）。
  - `[建议]` 使用 HPKE（RFC 9180，DHKEM-X25519 + ChaCha20-Poly1305），配合在 KEL 或 AgentCard 中发布的独立 X25519 加密公钥。A2A AgentCard 可以通过 extension 字段携带这把公钥。
  - 是否引入预密钥以获得离线前向保密，列为未决问题（第 5 节）。
  - 算法选择属于 ANetCore（C4）的决定，本报告只列约束。
- **元数据最小化。**
  - `kind`、`interaction_id` 进入密文。`relay_message` 的相应列删除或置空；`RelayKind*` 常量从 hub 移到 ANetCore/daemon。
  - `completed_task` 的派生随之删除（4.7）。
  - 联邦 `Envelope` 去掉 `from_aid / kind / interaction_id`（`federation.go:107-124`），签名原像同步修改（`federation.go:128-144`）。
- **发送方认证的取舍。**

| 方案 | hub 看到 | 能做的防护 | 代价 |
|---|---|---|---|
| a. 认证发送：`/relay/send` 要求对 `(send, to_aid, H(ct), ts, hub_aid)` 的 KEL 签名 | 谁发给谁、何时、多大 | 按发送方与收件方限流、配额、封禁；可撤回自己的未投递消息 | hub 掌握通信关系图 |
| b. 匿名发送（sealed sender） | 只有收件人 | 只能按 IP 或收件人限流；需要收件方预先发放投递令牌才能控制垃圾 | 实现复杂；滥用处置弱 |

  `[建议]` 第一阶段采用 a，并在文档与 UI 中如实写明"hub 可见通信关系元数据"。b 列为后续选项。

- **限流与配额** `[建议]`：
  - 每发送方令牌桶；每收件邮箱设置条数与字节上限（超出返回 429 或 507，不静默丢弃）。
  - 单条上限从 1 GiB 下调，例如 16 MiB。更大的附件改走 p2p 直连，或走加密分块。
  - 这些阈值在应用层实现，不依赖部署侧 nginx。
- **poll/ack 挑战修正** `[建议]`：
  - 原像加入 `hub_aid` 与请求体哈希（ack 的 ids、poll 的 limit）。
  - 服务端缓存 `(aid, ts, sig)` 至窗口结束，拒绝重放。
  - 这是 `relayauth` 的字节级变更，需同步更新 `relayauth_test.go` 中的钉死字节测试。
- **保留期** `[建议]`：
  - ack 即删，不再保留已投递行 7 天。未投递行设置 TTL（例如 14 天），到期删除。
  - relay 表启用 `PRAGMA secure_delete=ON`。
  - `hub-db-roll.sh` 的整库备份排除 `relay_message`：备份前复制库并 `DELETE`，或把 relay 拆到单独的库文件 `relay.db`，只备份 `hub.db`。
- **hub 侧不再解码 payload。** 删除 hub 对 `delegation` 包的依赖：访客模式（4.4）与 admin 采集（4.6）目前是仅有的解码方。之后可以加一条静态检查，确认 `ANetHub/internal/aghub` 与 `internal/admin` 不 import `ANetCore/delegation` 和 `tsir`，作为回归护栏。

### 4.3 评价：公开时能携带什么

**目标。** 评价仍可由任何第三方独立验证"这是某个真实交互的真实对端给出的评分"，但不公开交互内容。

**公开评价记录** `[建议]`：

| 字段 | 来源 | 是否签名覆盖 | 说明 |
|---|---|---|---|
| `interaction_id` | receipt / review | 是 | 由 16 字节随机数生成（`ANet/internal/daemon/delegation.go:173-179`），不含内容 |
| `subject_aid`、`reviewer_aid` | review | 是 | 公开通信关系；是否假名化见第 5 节 |
| `rating` | review | 是 | 1..5（`ANetCore/evidence/evidence.go`，`RatingMin/Max`） |
| `comment` | review | 是（`evidence.go:143-152`） | 评价者本人撰写、本人签名，公开是评价者的行为。建议加长度上限（例如 280 字符），CLI 与 UI 提示"此评语公开" |
| `created_at` | review | 是 | — |
| `receipt` 全对象 | provider 签名 | 是 | 含 requester、provider、`request_commit`、`result_commit`、completed_at |
| `receipt_cid` | review | 是 | 把评价锚定到该 receipt |
| 双方签名信封 | — | — | 用于验签 |
| 双方 KEL（联邦时） | — | — | 已有做法（`reputation.go:45-57`） |

**验证方式。**
- hub 与第三方都调用 `evidence.VerifyInterlock(rc, rv, nil, nil, provKEL, revKEL)`。该函数已支持传 nil 跳过内容绑定（`ANetCore/evidence/interlock.go:42-45`、`:77-95`），其余 8 项检查不变（`interlock.go:21-34`）。
- 内容绑定在 hub 侧的状态按"诚实效果状态"标为 `UNVERIFIED`（hub 不持有内容），而不是省略或显示为已验证。现有 UI 的"✓ 内容已验证"徽标（`AgentDetailDialog.tsx:71`、`:80`）必须删除。
- 若一方愿意把内容与盐私下交给某个第三方，该第三方可以离线重算承诺并得到 `OK`。这是选择性披露，不经过 hub。

**加盐承诺（必要）** `[建议]`：
- 由于 2.3 所述的字典确认问题，receipt 中的 `RequestCID / ResultCID` 需改为加盐承诺，例如 `commit = H(salt ‖ bytes)`，其中 salt 为 ≥128 bit，由需求方生成并在密文中传给提供方。也可以把随机 nonce 放进 TaskDoc 与 transcript 的哈希覆盖范围内。
- 注意 `tsir` 的规范 CID 原像目前排除全部 meta（`ANetCore/tsir/taskdoc.go:107-112`），而 `VerifyInterlock` 对原始字节做 `anetcid.Sum`（`interlock.go:79`）。nonce 放在哪里必须同时出现在两种计算中，否则两处 CID 会分歧。

**选项 B：浏览器持钥、客户端加密。**
- 浏览器生成临时 Ed25519/X25519 密钥对，以临时 AID 取得一个有 TTL 的邮箱；按 4.2 的 v2 信封把消息封给目标 agent 的加密公钥；用签名挑战轮询自己的邮箱，在本地解密。hub 只见密文。
- 目标 agent 必须显式开启接待（默认 0），默认只包括官方公开 agent。
- 需要解决的问题：
  1. **页面代码由 hub 提供。** 恶意或被入侵的 hub 可以下发会外传明文的脚本。浏览器端加密对"hub 运营者"这个威胁的保护，取决于代码来源是否独立于 hub。缓解办法是把客户端放在独立静态源（例如官网），加 SRI 与可复现构建；或做成浏览器扩展。UI 必须如实说明这一限制。`[推断]`
  2. 临时 AID 的注册与邮箱会成为匿名滥用入口，需要按 IP 与全局限流，并设置短 TTL。
  3. WebCrypto 对 Ed25519/X25519 的支持在各浏览器版本间不一致，可能需要纯 JS 实现（例如 noble 系列）。`[推断，未核对浏览器矩阵]`
- 代价：实现与维护量最大；安全收益受第 1 点限制。

**选项 C：官方公开 agent 直接提供 A2A 端点。** `[建议：推荐]`
- 官方公开 agent 部署在服务器上，本来就能作为 HTTPS 服务。它们直接暴露标准 A2A JSON-RPC 端点（含 CORS）。网站上的"试用"入口直接与该 agent 通信，hub 只在目录中列出它的 AgentCard。
- hub 完全不参与内容路径；这也符合"开放性来自官方公开 agent 与工具"的决定。
- 与 A2A 生态直接对齐：任何 A2A 客户端都能访问这些官方 agent。
- 限制：只覆盖官方或其他能做 HTTPS 服务的 agent，不覆盖 NAT 后的个人 agent。个人 agent 按原则 (3) 本来就默认不接待陌生人。

**推荐：A + C。** 删除 hub 代理式访客模式，由官方公开 agent 通过自身 A2A 端点提供试用体验。B 可作为以后"让个人 agent 接待浏览器访客"的可选模块，前提是先解决代码来源问题；若实现，应放在加法 tag 下。

## 6. 与 A2A 方向的衔接说明

- 按既定决定，外部 A2A 客户端通过本地 daemon 在 127.0.0.1 上的 A2A 接口进入网络。A2A 的 Task、Message、Artifact 以及 a2a-x402 的 `x402.payment.*` 元数据都在 daemon 之间的密文内传递。hub 不需要理解 A2A 对象。
- a2a-x402 中由商户 agent 调用 facilitator 完成验证与结算（`Refs/a2a-x402-spec-v0.2.md:137-140`）。若 hub 继续担任 facilitator，它会看到 PaymentPayload 与 PaymentRequirements。
  - `[建议]` 约定 `Resource.description` 只能取能力 id 或空值，不得由任务文本派生。现有网关已按能力 id 填写（`ANetHub/internal/aghub/gateway.go:259-261`；结构 `ANetCore/payment/payment.go:77-82`）。
  - 同时约定 PaymentRequirements 的其余自由文本字段同样不得携带任务内容。
- `DelegateReq.Payment` 目前随明文 delegate 一起经过 hub（`ANetCore/delegation/delegation.go:46-54`）。加密后进入密文；提供方 daemon 再单独调用 `/x402/settle`。
