### 4.2 已修的接口问题(`84b53d9`,`module/a2a/server.go`)

1. **JSON-RPC 路由不接受尾斜杠**。只注册了 `POST …/{aid}/jsonrpc`,TCK 的 JSON-RPC 客户端以接口 URL 为 base 发到
   `…/jsonrpc/`,得 404(0019 §4 第 2 条)。加同一 handler 的 `…/jsonrpc/{$}`,不用重定向。
2. **JSONRPC-SSE-002**:非 `application/json` 的请求体在 JSON-RPC 路由上回 AIP-193 形的 415(原因 `INVALID_REQUEST`),
   TCK 读到 code 415 判失败(0019 §4 第 3 条)。改为 JSON-RPC error 对象 `-32005`,`data` 含 ErrorInfo
   `CONTENT_TYPE_NOT_SUPPORTED`,`id` 为 null(未读请求体),HTTP 状态仍 415;REST 路由仍是 AIP-193 415,原因改为
   `CONTENT_TYPE_NOT_SUPPORTED`(§5.4)。`TestContentTypeAndRPCSlash` 覆盖两处,去掉任一修正即失败。

### 4.3 覆盖缺口:TCK 复用 messageId × 请求方去重

第 3、4 次仍有 18 个用例被 TCK 以 "Expected task state 'TASK_STATE_INPUT_REQUIRED' but got 'TASK_STATE_COMPLETED'"
跳过(历史、多轮、取消非终态任务、订阅到终态等)。原因:TCK 的 `create_working_task` 在整个会话里用同一个
messageId `tck-input-required-<会话>`、不带 contextId;anet 请求方对无 contextId 的新任务按 `(agent, messageId)`
去重(`internal/daemon/taskseam.go:17-22`、`:299`,有意为之:客户端重试时说不出 daemon 生成的 contextId),第二次
起拿到的是第一次那个任务,它此时已被后续用例完成。手工复现:同一 messageId 连发两次 `SendMessage`,返回同一
task id。

这与 0019 §4 第 7 条("去重只在客户端给了 contextId 时生效")的建议相反;而 A2A 规范要求 messageId 由创建方
保证唯一,TCK 的复用本身不合规范。**记录,不改**:是否放宽去重是设计选择(影响不带 contextId 的客户端重试语义),
交设计同步(B6-02 一类)决定;若保留现状,0019 §4 第 7 条应改写为"有意偏离"。
