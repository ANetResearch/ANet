## 2. 方法

**驱动方式。** 每个目标在 `f.Fuzz` 之前建一个真实的 hub(`aghub.Open` + `hubid` 身份 + `NewServer`,与 `wire2_helpers_test.go`
的 `newHubWithStore` 同构),请求走 `Server.Handler()` 的完整链(cors → wireContract → limitBody → mux),进程内
`ServeHTTP` + `httptest.NewRecorder`,不起监听端口。federation 用 `federation.New` 的真实 `Service`(对端 KEL 在建立时已钉住,
本地投递用测试里已有的 `fakeLocal`,它与内核一样核外层信封);admin 用真实 `admin.Store`/`HubDB`;taskboard 用真实
`taskboard.Store` 加真实 `aghub.Store` 做 KEL 验签。harness 在 `internal/aghub/fuzz_harness_test.go`。

**签名在运行时做。** 语料里只有"条款"(请求体、金额、时间偏移、篡改哪个头、谁签),签名由 harness 按当前时钟现签。一条语料对
每个 worker、每次重跑含义相同,变异作用在请求本身而不是只会验签失败的字节上。篡改类目标(relayauth v2、`/fed/v2/keys`、
taskboard 挑战、forward 信封)先签对,再按输入改头/改体/改目标/改动作,并据此算出"是否真的改过"(例如换成同值不算),断言
"改过的必须 401、没改且在时间窗内的不得 401、窗外的必须 401"。

**性质断言。** 每个目标除"不 panic、响应码在预期集合、不出现 5xx"外,都带与入口语义相关的性质(§3 表中列出)。账本类目标每条
输入后跑同一组不变量(`ledgerInvariants`):金额列全是 INTEGER(没有 REAL)、代理账户不为负、hub_due/hub_owed 不为负、每个账户的
条目之和等于余额(`anet reconcile` 的口径)、`Supply` 可计算且 `outstanding == balances`、`chain_agrees`。卡片类目标核索引:注册表、
技能/标签索引、fed_a2a_card 中凡"已验证"的行,都能用库里存的 KEL 由 `a2acard.Verify` 重新验证通过,且说的是它被存放的那个 AID。

**种子。** 用测试夹具构造的合法对象(`a2aCardFor`、`mintCard`、`mintKeySet`、`signedAuth`/`creditPayload`、`makeEvidence` 的同构、
`fedEnv`)作种子,ANetCore 的 `a2acard/testdata/golden-card.json` 作"结构完整、签名者不在本 hub"的卡片种子;金额、seq、时间
偏移另放边界值(0、2^63-1、2^64-1 附近、窗口两侧)。

**限流与环境。** fuzz 用的 hub 把注册/发送/联邦查钥的令牌桶和每签名方重放份额调大,否则几秒后只剩 429(限流另有单测)。SQLite
文件放在 tmpfs(`TMPDIR=/dev/shm/...`),提交不是 fsync;账本类目标仍只有每秒几十到一百多次(每条输入含多次签名、事务与不变量
查询)。运行中出现过几十秒 `execs` 不动,核对为 worker 在最小化新语料(Go 的 fuzz 在最小化期间不计数),不是挂住。

**方法上的两点教训。**
- Go 的整数变异每次只加减 1..100(`$GOROOT/src/internal/fuzz/mutator.go` 的 `mutateUInt`/`mutateInt`),不翻位、不取随机值。
  2^63、窗口边缘这类整数边界只能从种子来:FuzzHubKeys 第一轮 5 分钟 52,222 次没碰到 seq ≥ 2^63,加一条 `seq = 2^63-1` 的种子后
  第二轮 3 分 24 秒找到(发现 5);FuzzTaskboardChallengeTime 的 `2^63-1` 种子 1 秒内找到发现 6。字符串里的数字同理难以变到
  2^63 以上:FuzzHubPublicRoutes 以 `from=9223372036854775807` 为种子跑了 75,049 次没有越过去,发现 4 靠的是 `2^64-1` 的边界种子。
- hub 状态在 worker 内跨输入累积,最小化也在同一个 worker 里做,所以依赖累积状态的失败会被最小化成"最后一根稻草"(发现 3 的
  原始最小化输入是一张 10 元的普通收据,单独跑不复现)。这种情况把 testdata 里的语料改写成单条即可复现的输入,文件名按 Go 的
  规则用内容 sha256 的前 16 位重算,并在 §4 注明。

## 4. 发现与修复

行号是 `integ/round6`(ANetHub `cf58c50`)上的。每条的"mutation"是在工作树的副本里去掉修复重跑回归(不用 git stash),均变红。

**发现 1 —— `/x402/settle` 接受付给 hub 自己的付款,发放链从此对不上。** FuzzHubX402Facilitator 第二轮 4 分 24 秒、19,931 次时
失败,语料 `testdata/fuzz/FuzzHubX402Facilitator/eae7515b52aa1a9e`(金额 10,收款方选择子 `.` 即本 hub;单独可复现)。根因:
`SettleWithRequirements`(`internal/aghub/facilitator.go:394`)与 `VerifyWithRequirements`(`:801`)不拒收款方为本 hub 的要求;
`settleAuth` 把它当本地收款(`:541` `local := auth.PayTo == hubAID`),记到 hub 自身账户并写条目(supply 的 redeemed 上升),而发放链
的退出事件只在跨 hub 分支追加(`:616-620`),兑付的那一条由 `Redeem` 自己写。结果 `chain_agrees` 永久为 false,也没有兑付记录与
reference。任何人拿到付款人签给 hub 的兑付授权(即 `/x402/redeem` 的载荷)都可以抢先投到 `/x402/settle`;授权窗口过后付款人也补不上
兑付记录。修复(`c1db14b`):新增 `payeeIsThisHub`,Settle 与 Verify 在转发给对端之前就对"要求的收款方是本 hub"回
`payee_mismatch`;`Redeem` 直接调 `settleAuth`,不受影响。回归:`TestAPaymentToTheHubIsOnlyARedemption`(verify/settle 均拒、不动账、
同一授权仍可兑付)、`TestAPaymentToTheHubIsNotForwardedToAPeer`(入口 hub 不转发)。

**发现 2 —— 对端收据付给本 hub 时照样清算。** FuzzHubClearFromPeer 的种子阶段就红(当时有一条收款方选本 hub 的种子;随后把它改掉,
想让模糊阶段自己找,5 分钟内先撞上的是发现 3)。以手写语料 `testdata/fuzz/FuzzHubClearFromPeer/f89de6d8dedcb7f7` 保留。根因:
`ClearFromPeer`(`facilitator.go:987`)对 `rec.PayTo` 不设防,付给本 hub 时 hub 账户一进一出(`:1030` 与 hub 行的扣减),对端被记为
欠款,发放链却记一笔无账户持有的发行(`:1075`),`chain_agrees` 同样变 false。入口 hub 按商户给的要求(收款方可填成入口 hub 自己)
转发到对端账本、对端回的收据就是这样。修复(`c1db14b`):`ClearFromPeer` 拒收 `PayTo` 为本 hub 的收据(`payee_mismatch`),发现 1 的
修复另使这种付款不再被转发。回归:`TestAPeerReceiptPayingThisHubIsNotCleared`。

**发现 3 —— 累计发行没有上界,`/x402/supply` 一直 500(即 0030 §3 N2)。** FuzzHubClearFromPeer 第一轮 2 分 27 秒、8,202 次时
`Supply` 报 "integer overflow"。原始最小化输入依赖 worker 内累积状态,单独不复现;改写为单条可复现的
`testdata/fuzz/FuzzHubClearFromPeer/01736339790510ed`(一张 2^63-1-100 的对端收据付给未注册的 AID)。根因:`addToRow` 只约束单行,
`Supply`(`internal/aghub/redemption.go:318-345`,`:321` 对 hub 发行条目的 `SUM`)与发放链合计却是累计量;对端收据
(`facilitator.go:1030` 只核收款行)、运营者赠额(`GrantCredit`,`:1283` 只核该账户)、注册赠额(`GrantOnRegistration`,`:1267`)都
能把累计推过 int64。修复(`78bd35a`):新增 `issuanceRoom`(`amount.go`),"已发行 + 本次 ≤ MaxInt64",超出回 `invalid_amount`
且不动账;三个创造信用的入口都走它(`ClearFromPeer` 在事务内;注册到顶时照常注册、只是不给赠额,由调用方记日志)。`Store.Credit`
作为两种赠额之下的原语不检查,注释写明新调用方须自查。`TestPeerReceiptsInRangeCannotSumPastWhatALedgerHolds` 的"恰好到顶"一段
原来把受害者余额填到 MaxInt64,那时累计发行已超界;改为按供给填满(先碰到的是这道界),其后"再多 1 被拒"不变。回归:
`TestIssuanceCannotPassWhatTheSupplyCanAddUp`(超界收据被拒且 supply 可读;恰好填满可清算;再多 1 的收据与赠额被拒;到顶时的注册
不给赠额;`/x402/supply` 200)。mutation 分别去掉比较与注册赠额处的调用,均变红。

**发现 4 —— `GET /x402/issuance?from=` ≥ 2^63 时 500。** FuzzHubPublicRoutes 的边界种子(`from=18446744073709551615`)在种子阶段即红。
根因:`IssuanceSince`(`internal/aghub/issuance.go:193`,调用处 `witness.go:376`)把 uint64 交给 database/sql,高位为 1 的 uint64
被拒,未认证请求得到 500。修复(`7bca5a6`):seq 是 SQLite INTEGER,不会到 2^63,`from > MaxInt64` 直接回空页。回归:
`TestAnIssuanceCursorPastInt64IsAnEmptyPage`,另由该边界种子承担。

**发现 5 —— seq ≥ 2^63 的钥匙集让 `POST /agents/{aid}/keys` 500。** FuzzHubKeys 第二轮 3 分 24 秒、30,755 次,语料
`testdata/fuzz/FuzzHubKeys/84868313374056c7`(seq = 2^63+42)。根因:这样的集合能验签、能过高水位,写 `agent_keys.seq`
(`internal/aghub/keys.go:176`)时被 database/sql 拒;`/register` 里则表现为 `keys_error` 是原始 SQL 报错。修复(`fc66ec2`):seq 是毫秒
时间或上一个加一(`seal.NextSeq`),超过 MaxInt64 的按 `ErrKeysInvalid` 拒收(400),库里原有的集合不动;2^63-1 仍可存。回归:
`TestAKeySetSeqPastInt64IsRefusedNotA500`。

**发现 6 —— taskboard 挑战的时间窗在 ts 相距 2^63 时溢出放行。** FuzzTaskboardChallengeTime 1 秒、366 次,语料
`internal/taskboard/testdata/fuzz/FuzzTaskboardChallengeTime/cd72ed938e6a0969`(偏移 2^63+1;只在 handler 读时钟恰比 harness 晚 1 ms
时复现,所以另写确定性单测)。根因:`verifyChallenge`(`internal/aghub/server.go:1334-1338`)用 `|int64(now) - int64(ts)|` 判窗口,
差为 MinInt64 时取负仍为它自己,`skew > MaxSkew` 为假。`verifyV2`(`auth2.go:286`)与联邦查钥(`internal/federation/keys.go:96`)早已
先拒 `ts > 2^62`,这里漏了。影响低:要代理自己签出这样的 ts,放行也只在那一毫秒。修复(`a31b73c`):补同一条件,并拆出注入时钟的
`verifyChallengeAt`。回归:`TestAChallengeDatedHalfTheClockAwayIsRefused`(内部测试)。

**harness 自身的错(已改 harness、删语料,不计入发现)。** FuzzHubX402Facilitator 第一轮与 FuzzHubClearFromPeer 第二轮:把含非 UTF-8
字节的字符串放进要签的 CBOR 对象,`coredet` 拒绝编码——付款人/对端本来就签不出这种对象,harness 现在先 `strings.ToValidUTF8`。
FuzzHubX402Redeem 第一轮:reference 经 JSON 传输时非 UTF-8 字节被换成 U+FFFD,harness 却拿原字节比对;改为比对 JSON 往返后的值。

## 5. 其他观察(未修)

- **forward 没有时间窗。** `hForward`(`internal/federation/federation.go` 约 530 起)对 `TS` 不设窗,防重放只靠 7 天的载荷 CID 去重
  (`DedupeWindow`),而内层信封的 `exp` 可到 14 天(`seal.MaxMessageLifetimeMS`)。第 7–14 天重放一条对端签过的 forward 会再次入队,
  剩下的防线是收件 daemon 自己的 mid/exp 检查。前提是拿到那条 forward(对端之间走 TLS、对端在允许名单上)。
- **联邦查钥的重放集是全局的。** `replayGuard`(`internal/federation/keys.go`)一共 2^18 条、不按签名方分片;一个对端高速请求即可占满,
  其他对端得到 503 BUSY。内核的重放缓存已按签名方分片(F4),这里没有;对端在允许名单上。
- **taskboard 挑战不覆盖请求体、没有重放缓存。** wire-1 挑战只签 (action, aid, ts),±5 分钟内同一挑战可配另一份请求体再用(别的卡、
  标题、列)。前提是看到原请求;taskboard 是可选模块(`-tags taskboard`)。属设计取舍,记下供 §21 参考。
- **taskboard 的 WIP 上限只在认领时查。** reject 与 unblock 把卡放回 in_progress 时不查,受理人可以持有超过 `WIPLimit` 张进行中的卡;
  认领时的 WIP 计数也在 `mutate` 事务之外(并发可越过)。模糊测试的性质里没有把它当违例,因为"退回的工作仍算受理人的"也说得通。
- **卡片 seq ≥ 2^63 以数据库报错文本拒收。** A2A 卡 `params.seq`、ADP 卡 seq、联邦卡写库时同发现 5 的原因失败,表现为
  `card_status: invalid` 附 "not stored: sql: converting argument …",不是 5xx,但报错不说人话。与发现 5 同样的显式检查可以一并补。

## 6. 未能覆盖的部分

- **并发。** 每个 worker 顺序执行输入,竞态(并发结算、认领 WIP、同一 CID 的并发 forward)不在模糊测试能触及的范围,现有并发单测
  (spotcheck0030、release_qa_e 等)仍是唯一覆盖。
- **联邦的出站与同步客户端。** `TryForward`、`askKeys` 对对端回答的解析、`syncCards`/`syncReviews`/v2 卡流的分页解码没有 fuzz;对端内容
  只在准入缝(`AdmitFed*`)一层被覆盖。
- **整数的远处。** Go 的整数变异每次 ±100,时间偏移、金额、seq 只在种子附近被探索;窗口正中与种子之间的大片区域没有随机覆盖。
- **大体量。** 每个字段截到 8–80 KiB;96 MiB 信封上限、1 MiB 注册体上限、`limitBody` 本身未由 fuzz 触及(有单测)。
- **限流与配额。** fuzz 用的 hub 放宽了令牌桶与重放份额,限流逻辑本身不在断言内。
- **邀请制 hub。** fuzz 用的 hub 开放注册,`invite.go` 的令牌解析与"邀请制下首次注册"路径未 fuzz。
- **admin 的其余路由。** harvest、sessions、vision、store、audit、capabilities、overview 不在 FuzzAdminAPI 的路由表里;
  `anet-hub-admin` 的离线恢复(`RestoreAgentsFromBackup`)不经网络,未覆盖。
- **网关的价格解析。** 卖家卡的价目是固定的几种(整数、字符串、2^63-1、负数、小数),卡上价格本身没有被 fuzz;ADP 卡准入属 core。
- **带有效签名的见证证明、签名的注销。** `/x402/witness` 只喂原始字节,`/agents/{aid}/deregister` 只验证了未签不得 200。
- **core 的解析器**(`seal.ParseOuter`、KEL 解码、`a2acard.Verify`、coredet)经由 hub 的输入被间接走到,但属 fz-core 的范围。
