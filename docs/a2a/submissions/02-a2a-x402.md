## T1 — Issue: activation header (X1)

**Title**

```
spec v0.2 §8: activation via X-A2A-Extensions does not work with A2A 1.0 servers
```

**Body**

````markdown
**Text.** §8: "Clients MUST request activation of this extension by including its URI in the
`X-A2A-Extensions` HTTP header."

**Problem.** A2A 1.0 (§3.2.6) defines the service parameter `A2A-Extensions`, carried as an HTTP header
by the HTTP bindings, as gRPC metadata by gRPC, and by a binding-defined mechanism for custom bindings.
`X-A2A-Extensions` is the A2A 0.3 spelling. A client that follows §8 literally gets no activation from
an A2A 1.0 server that does not map the legacy name; a2a-go v2's v1 handlers, for example, do not.
Because §3.1 recommends `required: true`, such a server then rejects the request with
`ExtensionSupportRequiredError` although the client asked for the extension. The MUST also cannot be
met over gRPC or any non-HTTP binding.

**Suggested text.** "Clients MUST request activation of this extension using the extension activation
mechanism of the A2A protocol version and binding in use: the `A2A-Extensions` service parameter for
A2A 1.0 and later (for HTTP-based bindings, the `A2A-Extensions` header), or the `X-A2A-Extensions`
header for A2A 0.3. Agents SHOULD accept both header names during the transition."

Happy to send a PR with this change if it is welcome.
````

## T2 — Issue: state machine gaps and "outcome unknown" (X4)

**Title**

```
spec v0.2 §7.1: missing transitions (SUBMITTED→FAILED, REQUIRED→FAILED, FAILED→REQUIRED) and no rule for an unknown settlement outcome
```

**Body**

````markdown
§7.1 allows `REQUIRED → REJECTED` and `REQUIRED → SUBMITTED → VERIFIED → COMPLETED | FAILED`.

1. `SUBMITTED → FAILED` is missing, but it is the common failure: invalid signature, wrong amount,
   insufficient funds. §9.2's own example (an expired authorization) fails before any
   `payment-verified`.
2. `REQUIRED → FAILED` is missing: a merchant whose quote expired before any payment arrived has no
   state to report.
3. `FAILED → REQUIRED` is missing, although §9 lets a merchant request payment again with
   `input-required`.
4. There is no rule for "the settlement outcome is not known" (facilitator timeout, transport error,
   asynchronous rail). An implementation has to choose between reporting `payment-failed`, which
   invites the client to pay again although the first payment may have gone through, and reporting
   nothing.

**Suggested change.** Add the three transitions and this rule: "A merchant MUST NOT report
`payment-failed` while the outcome of a settlement is unknown. It keeps the task in its current state
and retries settlement with the same payment payload until the facilitator returns a final result;
facilitators are expected to answer a repeated settlement of the same payload with its original
result."

(We implement the extension with an idempotent facilitator that answers a pending settlement with a
`settlement_pending` reason; happy to contribute the text as a PR.)
````

## T3 — Issue: examples use A2A 0.3 JSON (X3)

**Title**

```
spec v0.2: examples use the A2A 0.3 wire format; state which A2A versions the extension covers
```

**Body**

````markdown
All examples in `spec/v0.2/spec.md` use the A2A 0.3 form: `"kind": "task"`, `"kind": "message"`,
method `message/send`, lowercase states (`"input-required"`), `"role": "agent"`, parts with
`"kind": "text"`. A2A 1.0 uses ProtoJSON (A2A ADR-001): method `SendMessage`,
`"state": "TASK_STATE_INPUT_REQUIRED"`, `"role": "ROLE_AGENT"`, parts without `kind`.

Implementers of A2A 1.0 have to translate every example and may wonder whether the extension applies
to 1.0 at all. The metadata keys work unchanged in both versions.

Suggested change: state which A2A versions the extension applies to, and give the examples in the 1.0
form (keeping the 0.3 ones in an appendix if useful). Together with #150 (x402 v2 objects) this would
bring the examples up to date.
````

## T5 — Issue: proposal to add the `anet-credit` experimental scheme

**Title**

```
Proposal: add anet-credit (custodial ledger) to schemes/ as an experimental scheme
```

**Body**

````markdown
We would like to add a scheme document for `anet-credit` to `schemes/`, next to the Lightning, Spark
and UMA drafts, as an experimental scheme.

**What it is.** `anet-credit` moves an integer balance on a ledger kept by one hub. The hub is at the
same time the ledger, the facilitator and the custodian, and the document says so plainly; that is why
it is not called `exact`. The payer signs an authorization for one payment to one payee on one hub's
ledger (Ed25519 over deterministic CBOR); the merchant settles it with that hub's facilitator; the hub
moves the credit once and returns a receipt it signs.

**Why it may be useful to others.**
- It is used with this extension over A2A 1.0, with x402 v2 objects, payment and result on the same
  task.
- One settlement per authorization, and at most one settled authorization per payer and task binding:
  a concrete answer to "paying twice for one task" (the binding is a hash, so the facilitator does not
  learn task ids).
- No task content reaches the facilitator: requirements sent for settlement carry no resource
  description.
- It documents two deviations openly: the network identifier `hub:<AID>` has the CAIP-2 shape but a
  59-character reference (CAIP-2 allows 32), and a local signing service that accepts an unsigned
  selection (a2a-x402 has no message for "sign this selected option").

**Reference implementation.** <link to the anet v0.2.0 release> (hub facilitator and client).

Draft: <link to docs/a2a/x402-scheme-anet-credit.md at the v0.2.0 tag>

Would the maintainers accept it under `schemes/`? We will adapt the layout to the existing drafts.
````

## Optional — Issue on x402-foundation/x402 (activation header in transports-v2/a2a.md)

Only if the product owner wants this second venue. x402-foundation asks that issues be bug reports or
concrete proposals; this is a concrete bug.

**Title**

```
specs/transports-v2/a2a.md: activation uses X-A2A-Extensions and the v0.1 extension URI
```

**Body**

````markdown
`specs/transports-v2/a2a.md` ("Extension Declaration and Activation") tells clients to activate the
extension with `X-A2A-Extensions: https://github.com/google-a2a/a2a-x402/v0.1`.

- `X-A2A-Extensions` is the A2A 0.3 header. A2A 1.0 uses the `A2A-Extensions` service parameter
  (A2A specification §3.2.6), which HTTP bindings carry as a header of that name and gRPC as metadata.
  A 1.0 server that does not map the legacy name ignores the activation; with the extension declared
  `required`, it then rejects the request.
- The URI is the v0.1 one, while the objects in this document are x402 v2, which a2a-x402 v0.1 did
  not describe.

Suggested: name the `A2A-Extensions` service parameter (keeping `X-A2A-Extensions` as the 0.3 form),
and state which extension URI this transport corresponds to.
````
